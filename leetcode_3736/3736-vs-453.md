# LeetCode 3736 與 453：使陣列元素相等的操作差異

兩題都要求讓陣列中的所有元素相等，但**一次操作能改動的元素數量不同**，所以最佳策略與答案公式也不同。解題時應先確認操作規則，再決定共同目標。

- [3736. Minimum Moves to Equal Array Elements III（官方題目）](https://leetcode.com/problems/minimum-moves-to-equal-array-elements-iii/)
- [453. Minimum Moves to Equal Array Elements（官方題目）](https://leetcode.com/problems/minimum-moves-to-equal-array-elements/)

## 1. 規則與公式比較

設 `n` 為陣列長度、`sum` 為原始元素總和、`max` 與 `min` 分別為原始最大值與最小值。

| 比較項目 | 3736：Minimum Moves III | 453：Minimum Moves |
|---|---|---|
| 一次操作 | 選擇 1 個元素加 1 | 選擇恰好 n − 1 個不同元素，各加 1 |
| 每次總和增加量 | 1 | n − 1 |
| 解題觀點 | 個別向上補齊 | 等價轉換成單一元素減 1 |
| 最佳共同目標 | 原始最大值 | 等價減法模型中的原始最小值 |
| 最少操作次數 | `Σ(max − nums[i])` | `Σ(nums[i] − min)` |
| 化簡公式 | `n × max − sum` | `sum − n × min` |
| 時間／額外空間 | `O(n)`／`O(1)` | `O(n)`／`O(1)` |

> 453 並沒有允許減法。「降到最小值」是保留相同操作次數的數學轉換；實際執行仍然只會增加元素。

## 2. 同一個陣列，兩題得到不同答案

使用 `nums = [1, 1, 3]`，索引由 0 開始。

### 3736：一次只增加一個元素，需要 4 次

```text
索引       0  1  2
起始      [1, 1, 3]
           |          nums[0] +1
第 1 次   [2, 1, 3]
           |          nums[0] +1
第 2 次   [3, 1, 3]
              |       nums[1] +1
第 3 次   [3, 2, 3]
              |       nums[1] +1
第 4 次   [3, 3, 3]
```

| 元素索引 | 原始值 | 目標值 | 個別需要的操作次數 |
|---|---:|---:|---:|
| 0 | 1 | 3 | 2 |
| 1 | 1 | 3 | 2 |
| 2 | 3 | 3 | 0 |
| 合計 | | | **4** |

### 453：一次增加兩個元素，只需要 2 次

此時 `n = 3`，每次必須選擇 `n − 1 = 2` 個元素一起加 1。

```text
索引       0  1  2
起始      [1, 1, 3]
           |  |       nums[0]、nums[1] 各 +1；nums[2] 不動
第 1 次   [2, 2, 3]
           |  |       nums[0]、nums[1] 各 +1；nums[2] 不動
第 2 次   [3, 3, 3]
```

3736 必須分開支付前兩個元素各增加 2 的成本；453 一次就能同時增加這兩個元素。相同輸入分別需要 **4 次與 2 次**，因此不能直接共用答案公式。

## 3. 3736：為什麼補到原始最大值？

設最後共同值為 `T`。由於元素只能增加，原本最大的元素無法變小，因此：

```text
T >= max
```

指定目標 `T` 後，第 `i` 個元素需要增加 `T − nums[i]` 次。每次操作只改動一個元素，所以總成本恰好是：

```text
cost(T) = Σ(T − nums[i])
        = n × T − sum
```

若目標從 `max` 提高到 `max + k`，其中 `k > 0`，所有元素都必須額外增加 `k` 次，總共多出 `n × k` 次。因此最小可行目標 `max` 就是最佳選擇。

```text
3736 最少次數 = Σ(max − nums[i])
              = n × max − sum

[1, 1, 3]： (3 − 1) + (3 − 1) + (3 − 3) = 4
```

## 4. 453：為什麼可以轉換成單一元素減 1？

### 一次操作的等價圖解

以三個元素為例，選擇前兩個加 1，第三個保持不變：

```text
                        實際操作：前兩個元素各 +1
原始狀態 [a, b, c] --------------------------------> [a+1, b+1, c]
                                                        |
                                                        | 為觀察差距，全部減 1
                                                        v
                                                    [a, b, c-1]
                                                        ^
原始狀態 [a, b, c] -------------------------------------|
                        等價模型：第三個元素 -1
```

全部元素同時減去同一個數，不改變任意兩元素的差距，也不改變「是否全部相等」。所以：

```text
除了第 j 個元素，其餘全部 +1
                等價於
只有第 j 個元素 -1（忽略全體共同上升的部分）
```

**圖中的「全部減 1」只是數學上的觀察方式，不是題目中的額外操作，不需要計入次數。**

### 等價轉換不是把操作倒過來

這裡使用的是「共同位移」：換一個共同基準觀察數值，保留元素之間的差距，並非把實際操作反向執行。

可以想成所有人站在同一塊地板上：**地板一起升高，每個人相對地面的高度都增加，但彼此的身高差不變。** 等價模型就是扣掉這塊地板的共同高度。

例如從 `[1,2,3]` 出發，實際增加索引 0、1，或在等價模型中減少索引 2，分別得到：

| 觀察項目 | 實際狀態 `[2,3,3]` | 等價狀態 `[1,2,2]` |
|---|---:|---:|
| 索引 1 的值 − 索引 0 的值 | 1 | 1 |
| 索引 2 的值 − 索引 0 的值 | 1 | 1 |
| 索引 2 的值 − 索引 1 的值 | 0 | 0 |
| 是否全部相等 | 否 | 否 |

兩個狀態的實際數值不同，但所有成對差距相同。等價模型可用來計算最少次數，不能把其中的減法當成題目允許的實際操作。

### 多次操作的逐步對照

經過 `k` 次實際操作後，將實際狀態的每個元素減去 `k`，就得到對應的等價減法狀態。

| 次數 k | 實際操作 | 453 的實際狀態 | 實際狀態全部減 k | 等價模型的操作 |
|---:|---|---|---|---|
| 0 | 尚未操作 | `[1,1,3]` | `[1,1,3]` | 尚未操作 |
| 1 | 索引 0、1 各加 1 | `[2,2,3]` | `[1,1,2]` | 索引 2 減 1 |
| 2 | 索引 0、1 各加 1 | `[3,3,3]` | `[1,1,1]` | 索引 2 再減 1 |

每一次實際操作，都對應到一次等價減法；反過來也能由減法選中的索引決定實際操作要略過誰。兩邊會在相同次數達成全部相等，所以最少次數也相同。

### 從等價模型推導公式

轉換後只能減少單一元素，最終共同值 `t` 必須滿足 `t <= min`。指定 `t` 時：

```text
cost(t) = Σ(nums[i] − t)
        = sum − n × t
```

選擇最大的可行值 `min`，就能避免多餘減法。若再降到 `min − d`，其中 `d > 0`，每個元素都要額外減少 `d` 次，總共多出 `n × d` 次。

```text
453 最少次數 = Σ(nums[i] − min)
             = sum − n × min

[1, 1, 3]： (1 − 1) + (1 − 1) + (3 − 1) = 2
```

## 5. 453 的實際最終值可能超過原始最大值

不要把等價模型中的最小值，誤當成實際操作的最終值。最少操作為 `k` 次時：

```text
等價模型的最終共同值 = min
實際操作的最終共同值 = min + k
```

例如 `nums = [1,2,3]`，公式得到 `k = 6 − 3 × 1 = 3`。

| 次數 k | 此次增加的索引 | 實際狀態 | 等價狀態：實際值全部減 k |
|---:|---|---|---|
| 0 | — | `[1,2,3]` | `[1,2,3]` |
| 1 | 0、1 | `[2,3,3]` | `[1,2,2]` |
| 2 | 0、2 | `[3,3,4]` | `[1,1,2]` |
| 3 | 0、1 | `[4,4,4]` | `[1,1,1]` |

對應的操作流程如下：

```text
[1,2,3]
   | 索引 0、1 各 +1
   v
[2,3,3]
   | 索引 0、2 各 +1
   v
[3,3,4]
   | 索引 0、1 各 +1
   v
[4,4,4]
```

實際共同值為 `min + k = 1 + 3 = 4`，高於原始最大值 `3`。所以 453 不能套用「直接補到原始最大值」的策略。

## 6. 相同答案不代表兩題相同

| 輸入 | 3736：n × max − sum | 453：sum − n × min | 觀察 |
|---|---:|---:|---|
| `[1,2,3]` | 3 | 3 | 次數相同，操作與實際最終值不同 |
| `[1,1,3]` | 4 | 2 | 453 可以同時增加兩個較小值 |
| `[1,3,3]` | 2 | 4 | 453 無法只增加唯一的較小值 |
| `[4,4,5]` | 2 | 1 | 453 一步即可得到 `[5,5,5]` |
| `[7]` | 0 | 0 | 單元素已經全部相等 |
| `[7,7,7]` | 0 | 0 | 不需要操作 |
| `[2,5]` | 3 | 3 | n = 2，兩題每次都是一個元素加 1 |

當 `n = 2` 時，`n − 1 = 1`，兩題操作規則完全相同。一般長度下，兩題答案相同的條件為：

```text
n × max − sum = sum − n × min
             ⇔ 2 × sum = n × (max + min)
```

也就是平均值剛好等於最大值與最小值的中點。例如 `[1,2,3]` 恰好符合，但這不代表兩題能共用公式。

## 7. 常見誤解與反例

### 誤解一：453 可以少選元素，或重複選同一個位置

453 每次必須選擇**恰好 `n − 1` 個不同元素**，各增加 1。不能少選，也不能把同一個位置重複選取來湊數。

例如 `[1,3,3]` 的長度為 3，每一步必須增加兩個不同位置：

```text
[1,3,3] → [2,3,3] → [3,3,3]
           ^           ^
       每一步都只增加索引 0
```

這是 3736 的合法流程，但不符合 453。453 想增加索引 0，就必須同時增加另一個位置，因此原本的最大值也可能繼續上升。這正是兩題雖然都只能增加，卻不能都採用「補到原始最大值」策略的原因。

### 誤解二：補到最大值的總差距除以 n − 1 就是答案

容易產生的錯誤推論是：「一次能增加 `n − 1` 個元素，所以把 3736 的答案除以 `n − 1`，再向上取整即可。」

問題在於，**總和增加 `n − 1`，不代表對原始最大值的差距就消除了 `n − 1`**。增加哪些位置受到限制，還可能推高最大值。

以 `[1,3,3]` 為反例：

```text
補到原始最大值的總差距 = (3−1) + (3−3) + (3−3) = 2
錯誤推算               = 向上取整(2 / 2) = 1 次
453 正確答案           = (1−1) + (3−1) + (3−1) = 4 次
```

合法且達到最少次數的流程如下，索引由 0 開始：

```text
[1,3,3]
   | 索引 0、1 各 +1
   v
[2,4,3]
   | 索引 0、2 各 +1
   v
[3,4,4]
   | 索引 0、1 各 +1
   v
[4,5,4]
   | 索引 0、2 各 +1
   v
[5,5,5]
```

共 4 次，每一步都增加兩個不同位置。最終值也符合前述關係：`min + k = 1 + 4 = 5`。

### 誤解三：只計算 max − min 就足夠

最大值與最小值的差距，只能描述兩端相隔多遠，沒有計入其他元素及重複值的數量。

| 輸入 | max − min | 3736：向上差距總和 | 453：向下差距總和 |
|---|---:|---:|---:|
| `[1,1,3]` | 2 | 4 | 2 |
| `[1,3,3]` | 2 | 2 | 4 |

兩組陣列的長度、最大值、最小值完全相同，卻得到不同答案。3736 必須計入每個較小值的補齊成本；453 的等價模型則必須計入每個較大值的減少成本。

### 誤解四：讓元素相等都應該選平均數或中位數

共同目標取決於操作規則，不能僅憑「讓所有元素相等」就套用其他題目的策略。

| 操作規則 | 最佳目標或觀點 | 原因 |
|---|---|---|
| 單一元素只能加 1，如 3736 | 原始最大值 | 更小的目標不可達，更大的目標增加成本 |
| 單一元素只能減 1 | 原始最小值 | 更大的目標不可達，更小的目標增加成本 |
| 單一元素可加 1 或減 1，每次成本相同 | 中位數 | 最小化所有元素到目標的絕對差總和 |
| 其餘 n − 1 個元素各加 1，如 453 | 等價模型中的原始最小值 | 每一步等價於單一元素減 1 |

可增減的情境若長度為偶數，排序後兩個中央值之間的任何整數目標都能達到相同最小成本。

平均數也不是這兩題必須達到的目標，因為**兩題都沒有總和守恆的限制**：3736 每次總和增加 1，453 每次增加 `n − 1`。以 `[1,1,3]` 為例，原始平均數為 `5/3`，而兩題都能以合法操作達到整數共同值 `3`。

若另一題規定「從一個元素減 1，轉移給另一個元素」，總和才會保持不變；此時若能達成全部相等，共同值必須是原始平均數，但是否可行仍須檢查整數性與操作限制。

## 8. C# 實作與整數範圍

程式結構都可以使用「找極值，再累加差距」，但極值與相減方向不同。以下是獨立教學片段，假設輸入符合各題的非空陣列限制；可放入解題類別中使用，沒有修改專案現有方法。

```csharp
// 3736：個別向上補到原始最大值。
public static long MinMoves3736(int[] nums)
{
    int max = nums.Max();
    long moves = 0;

    foreach (int num in nums)
    {
        moves += (long)max - num;
    }

    return moves;
}

// 453：等價於個別向下降到原始最小值。
public static long MinMoves453(int[] nums)
{
    int min = nums.Min();
    long moves = 0;

    foreach (int num in nums)
    {
        moves += (long)num - min;
    }

    return moves;
}
```

- 兩個方法都掃描兩次，時間仍為 `O(n)`，額外空間為 `O(1)`，不需要排序，也不修改輸入。
- `Max()` 與 `Min()` 使用 LINQ；此 .NET 專案已啟用隱含 using。其他環境可加入 `using System.Linq;`。
- 3736 的限制為長度與數值皆介於 1 到 100，答案上界為 `99 × 99 = 9801`，現有專案使用 `int` 足夠。
- 453 的長度可達 `10^5`，元素範圍為 `−10^9` 到 `10^9`。題目保證答案能放進 32 位元整數，但 `sum` 與 `n × min` 的中間值仍可能溢位。
- 若直接使用化簡公式，應以 `long` 累加總和，並寫成 `(long)n * min` 或 `(long)n * max`；只在最後把已溢位的 `int` 結果轉成 `long` 無法補救。上面的片段也在相減前先轉成 `long`。
- 片段刻意回傳 `long` 以展示安全計算；提交到 LeetCode 時應配合平台的 `int` 回傳簽章，確認題目範圍後轉型。

## 9. 記憶方式

```text
3736：一次一個加 1
        → 向上補齊
        → 找原始最大值
        → 加總 max − nums[i]

 453：一次其餘全部加 1
        → 等價於一個減 1
        → 在等價模型中找原始最小值
        → 加總 nums[i] − min
```

閱讀這類題目時，先問「一次必須改動幾個元素、每個元素改動多少」，才能正確決定成本模型與公式。
