# LeetCode 1235 — Maximum Profit in Job Scheduling

![.NET 10](https://img.shields.io/badge/.NET-10.0-512BD4)

本專案使用 C# 解答 LeetCode 1235「Maximum Profit in Job Scheduling（規劃兼職工作）」。題目要求從多份帶有開始時間、結束時間與報酬的工作中，選出時間互不重疊的集合，使總報酬最大。

## 題目說明

有 `n` 份工作，第 `i` 份工作的資訊為：

- `startTime[i]`：開始時間。
- `endTime[i]`：結束時間。
- `profit[i]`：完成後可得到的報酬。

要選出若干份工作，使任兩份被選工作都不重疊，並回傳可取得的最大報酬。

若一份工作在時間 `X` 結束，另一份工作也在時間 `X` 開始，兩者可以連續執行，不視為重疊。因此相容條件是：

```text
previousEndTime <= currentStartTime
```

### 官方範例一

```text
startTime = [1,2,3,3]
endTime   = [3,4,5,6]
profit    = [50,10,40,70]
輸出：120
```

選擇工作 `[1,3)`，報酬 `50`，再選擇 `[3,6)`，報酬 `70`。兩份工作在時間 `3` 首尾相接，總報酬為 `120`。

```text
時間：1----2----3----4----5----6
工作 A：[========)                 profit = 50
工作 D：          [==============) profit = 70

總報酬：50 + 70 = 120
```

### 官方範例二

```text
startTime = [1,2,3,4,6]
endTime   = [3,5,10,6,9]
profit    = [20,20,100,70,60]
輸出：150
```

選擇 `[1,3)`、`[4,6)` 與 `[6,9)`，報酬為 `20 + 70 + 60 = 150`。

### 官方範例三

```text
startTime = [1,1,1]
endTime   = [2,3,4]
profit    = [5,6,4]
輸出：6
```

三份工作從同一時間開始，彼此重疊，只能選一份；其中報酬 `6` 最大。

## 限制條件

依 [LeetCode 1235 官方題面](https://leetcode.com/problems/maximum-profit-in-job-scheduling/description/)：

- `1 <= startTime.length == endTime.length == profit.length <= 5 * 10^4`。
- `1 <= startTime[i] < endTime[i] <= 10^9`。
- `1 <= profit[i] <= 10^4`。

這些限制直接影響設計：

- `n` 最多為 `50,000`，無法列舉所有工作子集合；`O(2^n)` 不可行。
- 時間上限很大，不適合建立以每個時間點為索引的 DP 陣列。
- 必須先排序工作，再用二分搜尋或優先佇列把每次轉移控制在 `O(log n)`。
- 最壞情況可選取全部 `50,000` 份工作，每份報酬 `10,000`，總和為 `500,000,000`，仍在 C# `int` 範圍內。

三個公開解法都依照 LeetCode 的合法輸入契約設計：三個陣列非空且長度相同。空陣列與長度不一致不屬於題目輸入，因此程式不額外加入例外處理。

## 解題概念與出發點

### 1. 這是加權區間排程

每份工作都是一個帶權區間：

```text
[startTime, endTime) -> profit
```

目標不是選最多工作，而是讓權重總和最大。短工作不一定比較好，高報酬工作也不一定應該立刻選取。

例如：

```text
[1,3) profit 50
[2,5) profit 100
[3,4) profit 70
[4,6) profit 60
```

只看單份工作，`100` 最大；但選擇 `[1,3)`、`[3,4)`、`[4,6)` 可得到 `50 + 70 + 60 = 180`。因此單純按報酬、長度或結束時間貪心都不能保證正確。

### 2. 排序讓「相容工作」形成可搜尋的範圍

若按結束時間排序，與目前工作相容的舊工作會形成一段前綴：

```text
endTime <= currentStartTime | endTime > currentStartTime
       相容前綴          |      衝突區段
```

若按開始時間排序，目前工作之後可銜接的工作會形成一段後綴：

```text
startTime < currentEndTime | startTime >= currentEndTime
         衝突區段          |       相容後綴
```

兩者都能使用 lower-bound 形式的二分搜尋，在 `O(log n)` 內找出分界。

### 3. 每份工作都只有「選」與「不選」

兩種 DP 解法都以同一個核心決策為基礎：

```text
最佳答案 = max(
    不選目前工作時的最佳答案,
    選目前工作的報酬 + 相容區段的最佳答案)
```

差別只在於相容答案位於目前工作的左側前綴，還是右側後綴。

### 4. 為何三個輸入陣列保持不變？

三種解法都需要排序，但不直接重排 `startTime`、`endTime`、`profit`。程式先把每份工作複製為內部的三元素陣列：

```text
[startTime[i], endTime[i], profit[i]]
```

後續只排序內部資料，因此呼叫完成後，使用者提供的三個陣列內容與順序都不變。測試框架會明確驗證這個契約。

## 解法一：結束時間前綴 DP

### 設計說明

`JobScheduling` 保留既有解法的方向：先按結束時間升序排序，令：

```text
dp[i] = 排序後前 i 份工作可取得的最大報酬
```

`dp[0] = 0`，表示沒有考慮任何工作時報酬為零。對排序後第 `i - 1` 份工作：

1. 使用 `BinarySearch` 找出結束時間小於等於目前開始時間的工作數量 `k`。
2. 不選目前工作時，答案是 `dp[i - 1]`。
3. 選目前工作時，答案是 `dp[k] + currentProfit`。
4. 取兩者較大值。

轉移式：

```text
dp[i] = max(dp[i - 1], dp[k] + jobs[i - 1].profit)
```

`BinarySearch` 回傳的是相容前綴的「工作數量」，不是最後一份相容工作的零起始索引，因此可直接拿來存取 `dp[k]`。

### 二分搜尋邊界

搜尋範圍是 `[0, right)`，目標為第一個：

```text
jobs[position].endTime > currentStartTime
```

因此位置左側全部滿足 `endTime <= currentStartTime`。若所有舊工作都相容，回傳值就是 `right`；若沒有任何工作相容，回傳 `0`。

首尾相接的工作必須視為相容，所以判斷使用 `<=`，不能寫成 `<`。

### 官方範例一演示

依結束時間排序後：

| 位置 | 工作區間 | 報酬 |
|---:|---:|---:|
| 1 | `[1,3)` | 50 |
| 2 | `[2,4)` | 10 |
| 3 | `[3,5)` | 40 |
| 4 | `[3,6)` | 70 |

DP 過程：

| `i` | 相容數量 `k` | 不選 `dp[i-1]` | 選取 `dp[k] + profit` | `dp[i]` |
|---:|---:|---:|---:|---:|
| 1 | 0 | 0 | 0 + 50 = 50 | 50 |
| 2 | 0 | 50 | 0 + 10 = 10 | 50 |
| 3 | 1 | 50 | 50 + 40 = 90 | 90 |
| 4 | 1 | 90 | 50 + 70 = 120 | 120 |

最後回傳 `dp[4] = 120`。

### 正確性說明

考慮排序後的前 `i` 份工作，最佳解只有兩種可能：

1. 不包含第 `i` 份工作，此時最佳值就是前 `i - 1` 份工作的答案 `dp[i - 1]`。
2. 包含第 `i` 份工作。為避免重疊，其餘工作只能從結束時間不晚於目前開始時間的前綴選取；該前綴最佳值是 `dp[k]`，加上目前報酬即為 `dp[k] + profit`。

轉移取兩種完整且互斥情況的最大值。由 `dp[0] = 0` 開始逐步計算，可得到全部工作的最佳答案。

### 複雜度與副作用

- 排序：`O(n log n)`。
- 每份工作一次二分搜尋：總計 `O(n log n)`。
- 時間複雜度：`O(n log n)`。
- 額外空間複雜度：`O(n)`，包含內部工作陣列與 DP 陣列。
- 是否修改輸入：否。

## 解法二：開始時間後綴 DP

### 設計說明

`JobScheduling2` 改為按開始時間升序排序，令：

```text
dp[i] = 從排序後第 i 份工作開始考慮，可取得的最大報酬
```

因為狀態依賴右側的未來工作，所以從右向左計算。對第 `i` 份工作：

1. 使用 `FindNextJobIndex` 找到第一份 `startTime >= currentEndTime` 的工作索引 `next`。
2. 不選目前工作時，答案是 `dp[i + 1]`。
3. 選目前工作時，答案是 `currentProfit + dp[next]`。
4. 取兩者較大值。

轉移式：

```text
dp[i] = max(dp[i + 1], jobs[i].profit + dp[next])
```

`dp[n] = 0` 是超出最後一份工作的空後綴，亦讓「沒有下一份相容工作」可以直接使用同一轉移式。

### 官方範例一演示

依開始時間排序後：

| 索引 `i` | 工作區間 | 報酬 | 下一份相容工作 `next` |
|---:|---:|---:|---:|
| 0 | `[1,3)` | 50 | 2 |
| 1 | `[2,4)` | 10 | 4 |
| 2 | `[3,5)` | 40 | 4 |
| 3 | `[3,6)` | 70 | 4 |

由右向左：

```text
dp[4] = 0
dp[3] = max(0, 70 + 0) = 70
dp[2] = max(70, 40 + 0) = 70
dp[1] = max(70, 10 + 0) = 70
dp[0] = max(70, 50 + dp[2]) = 120
```

第 0 份工作在時間 `3` 結束，第 2 份工作也在時間 `3` 開始，二分搜尋會正確把索引 `2` 視為可銜接位置。

### 正確性說明

考慮從索引 `i` 開始的所有工作，最佳解同樣分成兩種：

1. 不包含工作 `i`，剩餘最佳答案為 `dp[i + 1]`。
2. 包含工作 `i`，之後只能從第一份開始時間不早於目前結束時間的工作 `next` 起選取，答案為 `profit[i] + dp[next]`。

二分搜尋保證跳過全部衝突工作，而且不漏掉任何相容工作。從已知的空後綴 `dp[n]` 反向計算，最終 `dp[0]` 即為全體工作的最佳答案。

### 複雜度與副作用

- 排序：`O(n log n)`。
- 每份工作一次二分搜尋：總計 `O(n log n)`。
- 時間複雜度：`O(n log n)`。
- 額外空間複雜度：`O(n)`。
- 是否修改輸入：否。
- 特性：狀態直接描述「從現在往後」，與 LeetCode 官方提示的後綴 DP 方向一致。

## 解法三：優先佇列掃描

### 設計說明

`JobScheduling3` 不建立 DP 陣列，而是按開始時間掃描工作。使用最小優先佇列保存仍可能影響未來的方案：

```text
(EndTime, TotalProfit)
```

- `EndTime`：此方案最後一份工作的結束時間，也是優先順序。
- `TotalProfit`：選到這份工作為止的累積報酬。
- `bestCompletedProfit`：在目前開始時間之前已結束的所有方案中，最大累積報酬。

掃描每份工作時：

1. 從佇列取出所有 `EndTime <= currentStartTime` 的方案。
2. 用它們更新 `bestCompletedProfit`。
3. 目前工作可接在任一已完成最佳方案之後，因此新總報酬為 `bestCompletedProfit + currentProfit`。
4. 將新方案以目前結束時間放回佇列。

所有工作掃描完後，再排空佇列以取得全域最大報酬。

### 為何只保留一個 `bestCompletedProfit`？

當某方案已在目前開始時間之前結束，它也會在所有更晚的工作開始前保持可用。若兩個已完成方案分別得到 `80` 與 `100`，未來永遠只需要報酬較大的 `100`；較小值不可能產生更好的延伸結果。

尚未結束的方案則不能提前合併，必須留在優先佇列等待其結束時間到達。

### 官方範例一演示

按開始時間掃描：

```text
工作 [1,3), profit 50
  沒有已完成方案
  push(end=3, total=50)

工作 [2,4), profit 10
  end=3 尚未 <= start=2
  push(end=4, total=10)

工作 [3,5), profit 40
  pop(end=3, total=50)
  bestCompletedProfit = 50
  push(end=5, total=90)

工作 [3,6), profit 70
  沒有更多 end <= 3 的方案
  push(end=6, total=120)

掃描結束，排空佇列
  最大 total = 120
```

當開始時間恰好等於舊方案結束時間時，`<=` 條件會先取出舊方案，因此能正確建立 `50 + 70 = 120`。

### 正確性說明

掃描到開始時間 `S` 時，優先佇列已取出所有結束時間 `<= S` 的方案，`bestCompletedProfit` 因此等於所有可與目前工作銜接方案的最大報酬。

任何包含目前工作的最佳方案，都必須由一個已在 `S` 前結束的方案加上目前報酬；程式建立的 `bestCompletedProfit + currentProfit` 正是其中最大值。任何尚未結束的方案仍留在佇列，等待之後可能相容的工作。依開始時間依序處理後，所有合法方案都會被建立；最後排空佇列即可得到最大值。

### 複雜度與副作用

- 排序：`O(n log n)`。
- 每個方案最多入列、出列各一次：`O(n log n)`。
- 時間複雜度：`O(n log n)`。
- 額外空間複雜度：`O(n)`，包含內部工作陣列與優先佇列。
- 是否修改輸入：否。
- 特性：不需要 DP 陣列，以「已完成最佳值 + 仍在進行方案」表達狀態。

## 三種解法比較

| 解法 | 排序依據 | 核心狀態 | 相容工作查找 | 時間 | 額外空間 |
|---|---|---|---|---:|---:|
| 結束時間前綴 DP | 結束時間 | 前 i 份工作的最佳答案 | 二分搜尋相容前綴 | `O(n log n)` | `O(n)` |
| 開始時間後綴 DP | 開始時間 | 從 i 開始的最佳答案 | 二分搜尋相容後綴 | `O(n log n)` | `O(n)` |
| 優先佇列掃描 | 開始時間 | 已完成最佳值與進行中方案 | 依結束時間出列 | `O(n log n)` | `O(n)` |

選擇建議：

- 想從「已處理工作的最佳答案」理解加權區間排程，可使用解法一。
- 想把選取工作後的跳轉位置寫得直觀，可使用解法二。
- 想練習掃描線與優先佇列，或避免顯式 DP 陣列，可使用解法三。

三者都不修改輸入，且在題目上限內具有相同漸進時間與空間複雜度。
