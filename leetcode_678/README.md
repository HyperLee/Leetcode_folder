# 678. Valid Parenthesis String

[![LeetCode](https://img.shields.io/badge/LeetCode-678-orange?style=flat-square)](https://leetcode.com/problems/valid-parenthesis-string/)
[![Difficulty](https://img.shields.io/badge/Difficulty-Medium-yellow?style=flat-square)](https://leetcode.com/problems/valid-parenthesis-string/)
[![.NET](https://img.shields.io/badge/.NET-10.0-512BD4?style=flat-square)](https://dotnet.microsoft.com/)

使用 C# 實作「有效的括號字串」，並以雙索引堆疊、貪心上下界與動態規劃三種方法比較不同的狀態表示方式。`Main` 內含十組可直接執行的案例，會自動驗證三種解法的結果。

## 題目說明

給定一個只包含 `(`、`)` 與 `*` 的字串 `s`，判斷是否能把每個 `*` 分別視為以下任一內容，使整個字串成為有效括號字串：

- 一個左括號 `(`。
- 一個右括號 `)`。
- 空字串。

有效字串必須符合：

1. 每個左括號都有對應的右括號。
2. 每個右括號都有對應的左括號。
3. 左括號必須出現在與它配對的右括號之前。

官方範例：

| 輸入 | 輸出 | 一種可行解釋 |
|---|---:|---|
| `()` | `true` | 原字串已有效 |
| `(*)` | `true` | 將 `*` 視為空字串 |
| `(*))` | `true` | 將 `*` 視為左括號 |

## 限制條件

- `1 <= s.length <= 100`
- `s[i]` 只會是 `(`、`)` 或 `*`
- 本專案依題目契約處理合法且非空的輸入，不額外驗證 `null`、空字串或其他字元。

## 解題概念與出發點

### `*` 帶來的是「多種可能狀態」

一般括號題只需追蹤目前尚未配對的左括號數；遇到 `(` 加一，遇到 `)` 減一，而且任何前綴都不能降到負數。

本題的 `*` 可以讓未配對左括號數增加一、減少一或維持不變，因此掃描到同一位置時可能同時存在多個合法狀態。三種解法的差異，就在於如何保存或壓縮這些狀態：

- 雙堆疊保存可供配對的實際索引。
- 貪心只保存所有可能括號數的最小值與最大值。
- 動態規劃保存每個前綴所有可達的括號數。

### 為什麼不能只比較括號總數

有效括號除了數量相等，還要求順序正確。例如 `)(` 含有相同數量的左右括號，但第一個右括號出現時，前方沒有任何左括號可配對，因此無效。

相同限制也適用於星號。字串 `(*(` 中雖然可把 `*` 當成右括號，但該星號位於最後一個左括號之前，無法補足結尾的左括號。每種解法都必須保證任一前綴不會出現無法配對的右括號。

## 解法一：雙索引堆疊

### 設計說明

`CheckValidString` 使用兩個 `Stack<int>`：

- `leftParentheses` 保存尚未配對的左括號索引。
- `wildcards` 保存尚未使用的星號索引。

由左至右掃描：

1. 遇到 `(`，將索引放入左括號堆疊。
2. 遇到 `*`，將索引放入星號堆疊。
3. 遇到 `)`，優先彈出真正的左括號；若沒有左括號，再把一個較早的星號當成左括號。
4. 兩個堆疊都為空卻遇到 `)`，代表目前前綴不可能有效，立即回傳 `false`。
5. 掃描結束後，將剩餘星號當成右括號，逐一配對剩餘左括號。

最後一步必須比較索引。只有位於左括號之後的星號，才能當作它的右括號；若左括號索引大於星號索引，就不能形成合法配對。

### `Pop()` 為什麼可以使用 `>` 比較？

這裡比較的不是兩個堆疊的大小，而是 `Pop()` 從堆疊頂端取出的索引值。兩個堆疊宣告為 `Stack<int>`，而掃描字串時放入的是目前字元的 `index`：

```csharp
leftParentheses.Push(index);
wildcards.Push(index);
```

因此，`leftParentheses.Pop()` 與 `wildcards.Pop()` 都會回傳 `int`。C# 的方法呼叫本身可以是比較運算子的運算元，所以：

```csharp
if (leftParentheses.Pop() > wildcards.Pop())
{
    return false;
}
```

可以理解成先取出兩個索引，再比較它們：

```csharp
int leftIndex = leftParentheses.Pop();
int wildcardIndex = wildcards.Pop();

if (leftIndex > wildcardIndex)
{
    return false;
}
```

`Count` 與 `Pop()` 的用途不同：

| 成員 | 意義 |
|---|---|
| `Count` | 堆疊目前有幾個元素，也就是數量。 |
| `Pop()` | 移除堆疊頂端的元素，並回傳被移除的值。 |

#### 為什麼要比較索引？

字串索引越小，代表字元越早出現。若星號要被當成右括號 `)`，它就必須位於要配對的左括號 `(` 之後：

```text
左括號索引 < 星號索引
```

所以程式反過來檢查不合法的情況：

```text
左括號索引 > 星號索引
```

當這個條件成立時，代表星號出現在左括號之前，不能用它關閉該左括號，必須回傳 `false`。相同索引不會發生，因為同一個字元不可能同時被放入左括號堆疊與星號堆疊；因此程式檢查 `>` 就足夠。

例如 `s = "(*"`：

```text
索引：              0  1
字元：              (  *
leftParentheses：  [0]
wildcards：        [1]
```

取出後是 `leftIndex = 0` 與 `wildcardIndex = 1`，判斷 `0 > 1` 為 `false`。星號位於左括號之後，可以視為右括號：

```text
(*  →  ()
```

反過來，`s = "*("` 的堆疊內容為：

```text
leftParentheses：  [1]
wildcards：        [0]
```

此時 `leftIndex = 1`、`wildcardIndex = 0`，`1 > 0` 成立。星號在左括號之前，不能拿來關閉後面的左括號，因此字串無法有效。

#### 為什麼使用 `Pop()` 的頂端元素？

`Stack` 是後進先出（LIFO，Last In First Out）結構。由左至右掃描時，較晚出現的索引會位於堆疊頂端，因此 `Pop()` 會先取出目前最右側的未配對位置。

例如 `s = "(*("`：

```text
索引：              0  1  2
字元：              (  *  (
leftParentheses：  [0, 2]  // 頂端是 2
wildcards：        [1]     // 頂端是 1
```

程式先嘗試配對索引 2 的左括號與索引 1 的星號，得到 `2 > 1`，立即判定失敗。雖然星號可以關閉索引 0 的左括號，但索引 2 的左括號已經位於星號之後，沒有任何更晚的星號可以關閉它。

再如 `s = "((**"`：

```text
leftParentheses：  [0, 1]
wildcards：        [2, 3]
```

兩次配對依序取出 `(1, 3)` 與 `(0, 2)`，兩次都符合左括號索引小於星號索引，因此可以將兩個星號視為右括號：`((** → (())`。

`while` 的條件先確認兩個堆疊都不為空，保證呼叫 `Pop()` 時有元素可取。若剩餘左括號多於可用且位置合法的星號，迴圈結束後 `leftParentheses.Count` 仍大於零，最後的回傳判斷就會得到 `false`。反之，剩餘星號可以視為空字串，不會影響有效性。

### 正確性重點

- 遇到右括號時優先使用真正的左括號，可以保留用途較有彈性的星號。
- 堆疊頂端是目前最右側的未配對位置；從右向左配對剩餘左括號與星號，可讓最接近的合法位置先配對。
- 最後沒有剩餘左括號時，未使用的星號都可視為空字串，因此結果有效。

### 複雜度

| 項目 | 複雜度 | 說明 |
|---|---:|---|
| 時間 | `O(n)` | 每個索引最多被放入與取出堆疊各一次。 |
| 輔助空間 | `O(n)` | 最差情況需保存所有左括號或星號索引。 |

### 範例演示：`(*))`

| 索引 | 字元 | 左括號堆疊 | 星號堆疊 | 動作 |
|---:|:---:|---|---|---|
| 0 | `(` | `[0]` | `[]` | 保存左括號索引 |
| 1 | `*` | `[0]` | `[1]` | 保存星號索引 |
| 2 | `)` | `[]` | `[1]` | 優先與索引 0 的左括號配對 |
| 3 | `)` | `[]` | `[]` | 沒有左括號，將索引 1 的星號視為左括號 |

掃描結束後兩個堆疊皆空，因此回傳 `true`。

## 解法二：貪心上下界

### 設計說明

`CheckValidString2` 不保存每一種星號替換結果，而是維護目前所有仍可能形成有效前綴的狀態範圍。

對某一種固定的星號解釋方式而言，`open` 表示目前尚未配對的左括號數：

- 遇到 `(`，`open` 加一。
- 遇到 `)`，`open` 減一；如果減到負數，代表右括號沒有可以配對的左括號，這條解釋方式失效。
- 遇到 `*`，可以選擇讓 `open` 減一、維持不變或加一。

但是同一個前綴可能有很多種 `open`。因此程式不保存每一個數字，而只保存這些可達數字的兩端：

- `minimumOpen`：最少可能有幾個未配對左括號。
- `maximumOpen`：最多可能有幾個未配對左括號。

這兩個變數不是兩條獨立的替換路徑，而是用區間 `[minimumOpen, maximumOpen]` 壓縮所有可能狀態。例如區間 `[0, 2]` 代表目前可能有 `0`、`1` 或 `2` 個未配對左括號；它不表示程式同時選定了一條「最小路徑」與一條「最大路徑」。

可達數字會保持連續：初始狀態只有 `[0, 0]`；固定的 `(` 或 `)` 只會讓整個區間平移；`*` 則會讓每個狀態各自向下、維持或向上，因此合併後仍是連續區間。這就是只保存上下界仍不會漏掉中間狀態的原因。

### 三個分支逐行拆解

三個分支的重點不是直接決定星號的實際替換結果，而是計算這個字元可能把整個 `open` 範圍推到哪裡：

| 字元 | `minimumOpen` | `maximumOpen` | 原因 |
|:---:|---:|---:|---|
| `(` | `+1` | `+1` | 一定新增一個未配對左括號 |
| `)` | `-1` | `-1` | 一定需要配對一個左括號 |
| `*` | `-1` | `+1` | 可視為右括號、空字串或左括號 |

對應的核心更新程式如下：

```csharp
if (character == '(')
{
    minimumOpen++;
    maximumOpen++;
}
else if (character == ')')
{
    minimumOpen--;
    maximumOpen--;
}
else
{
    minimumOpen--;
    maximumOpen++;
}
```

#### `(`：兩個界限都加一

如果目前可達範圍是 `[l, h]`，讀到真正的左括號後，每一種可能都變成原本的數量加一，因此新範圍是 `[l + 1, h + 1]`。沒有任何星號選擇需要在這裡比較，所以 `minimumOpen` 與 `maximumOpen` 必須同步增加。

#### `)`：兩個界限都減一

讀到真正的右括號時，每一條仍可行的路徑都要拿一個左括號來配對，因此新範圍先計算為 `[l - 1, h - 1]`。如果整個範圍都低於零，表示任何解釋方式都沒有足夠的左括號，稍後的 `maximumOpen < 0` 會立即判定失敗。

#### `*`：下界減一，上界加一

星號有三種解釋方式：

| 星號解釋 | `open` 變化 | 對界限的影響 |
|---|---:|---|
| 當作右括號 `)` | `-1` | 提供新的最小可能值，所以 `minimumOpen--`。 |
| 當作空字串 | `0` | 產生介於上下界之間的狀態，不需要額外變數保存。 |
| 當作左括號 `(` | `+1` | 提供新的最大可能值，所以 `maximumOpen++`。 |

因此，若原本範圍是 `[l, h]`，星號更新後的原始範圍就是 `[l - 1, h + 1]`。這裡的 `l - 1` 只是「尚未排除不合法負值前」的數學下界；實際的未配對左括號數不能小於零，後續會再修正。

例如輸入只有 `*` 時，初始範圍 `[0, 0]` 先變成 `[-1, 1]`：`-1` 對應把星號當成右括號，但這會在空前綴上產生無法配對的右括號；`0` 對應空字串；`1` 對應左括號。排除負值後，真正保留的可能範圍是 `[0, 1]`。

### 為什麼要先檢查上界，再修正下界？

每次分支更新後，程式依序執行：

```csharp
if (maximumOpen < 0)
{
    return false;
}

minimumOpen = Math.Max(minimumOpen, 0);
```

1. `maximumOpen < 0`：`maximumOpen` 已經是所有可能狀態中的最大值。如果最大值仍為負數，代表整個可能範圍都小於零；換句話說，即使把先前能調整的星號全部盡量當成左括號，這個前綴仍有過多右括號，任何替換方式都無法成立，必須立即回傳 `false`。
2. `minimumOpen < 0`：負數不是合法的未配對左括號數，只代表某些星號被暫時當成右括號後，產生了無法維持有效前綴的路徑。因此使用 `Math.Max(minimumOpen, 0)` 丟棄負值，只保留非負的可達範圍。

這個順序不能顛倒。以 `s = ")"` 為例，更新後是 `minimumOpen = -1`、`maximumOpen = -1`。若先把 `minimumOpen` 修正為 `0`，會看起來像有一個可行狀態，但 `maximumOpen < 0` 已證明沒有任何狀態可行，所以必須先檢查上界。

掃描結束時，若 `minimumOpen == 0`，代表非負可達範圍包含 `0`，至少存在一種星號替換方式可以把所有左括號配對完成。若 `minimumOpen > 0`，表示每一種替換方式都還剩下左括號，不能形成有效字串。

### 正確性重點

對每個前綴而言，可達的未配對左括號數形成一段連續範圍，因此只需保留兩端。`(` 與 `)` 會同步平移兩端；`*` 的 `-1`、`0`、`+1` 三種變化則完整涵蓋右括號、空字串與左括號的用途。`maximumOpen < 0` 能立即排除右括號過多的前綴；最後下界為零，則代表至少存在一條選擇路徑能配對所有左括號。

### 複雜度

| 項目 | 複雜度 | 說明 |
|---|---:|---|
| 時間 | `O(n)` | 字串只掃描一次。 |
| 輔助空間 | `O(1)` | 只保存兩個整數上下界。 |

### 範例演示：`(*)` 與 `(*))`

下表同時列出分支更新後、尚未排除負值的原始下界，以及 `Math.Max` 修正後實際保留的下界：

| 處理後前綴 | 字元 | 原始 `minimumOpen` | `maximumOpen` | 修正後 `minimumOpen` | 判斷 |
|---|:---:|---:|---:|---:|---|
| 空字串 | — | 0 | 0 | 0 | 初始時沒有未配對左括號 |
| `(` | `(` | 1 | 1 | 1 | 一定新增一個左括號 |
| `(*` | `*` | 0 | 2 | 0 | 星號可當右括號、空字串或左括號 |
| `(*)` | `)` | -1 | 1 | 0 | 負下界被移除，仍可選擇讓星號保持空字串 |
| `(*))` | `)` | -1 | 0 | 0 | 零個未配對左括號仍然可達 |

在 `(*)` 這一步，若星號當成右括號，最後的真正右括號會讓數量落到 `-1`，這條路徑無效；若星號當成空字串，則可形成 `()`，留下 `0`；若星號當成左括號，則留下 `1`。因此修正後的範圍是 `[0, 1]`。

處理完整個 `(*))` 後，範圍為 `[0, 0]`，例如把星號當成左括號即可得到 `(())`，所以最後 `minimumOpen == 0`，回傳 `true`。

### 提前失敗案例：`())*`

這個案例說明為什麼後面的星號不能挽救已經失效的前綴：

| 處理後前綴 | `minimumOpen` | `maximumOpen` | 判斷 |
|---|---:|---:|---|
| `(` | 1 | 1 | 必須保留一個左括號等待配對 |
| `()` | 0 | 0 | 左右括號已配對 |
| `())` | -1 | -1 | `maximumOpen < 0`，所有可能狀態都已低於零，立即回傳 `false` |

程式在讀到第三個字元時就結束，不會把最後的 `*` 當成修復工具。因為星號出現在錯誤前綴之後，不能回到前面插入左括號來補救已經出現的右括號。

## 解法三：動態規劃

### 為什麼使用動態規劃？

如果直接為每個 `*` 枚舉三種解釋，`k` 個星號最多會產生 `3^k` 條替換路徑。這些路徑雖然選擇不同，卻可能在處理相同前綴後得到相同的「尚未配對左括號數」。只要目前的 `open` 相同，後續字元能否完成配對就完全相同，不必重複保存造成這個狀態的每一條路徑。

動態規劃的做法是合併這些共同狀態：每處理一個前綴，就保存所有仍可能出現的 `open` 數值。如此既不需要記住每個星號曾經如何選擇，也不會因為過早只選一條路徑而漏掉答案。

### 狀態定義與二維表格

`CheckValidString3` 建立 `bool[,] reachable`，其中：

```text
reachable[i, open]
```

表示：

- `i`：已處理的字元數，也就是前綴 `s[0..i)` 的長度；第 `i` 列代表這個前綴。
- `open`：這個前綴結束後，尚未配對的左括號 `(` 數量；第 `open` 欄代表一種可能數量。
- `true`：至少存在一種星號替換方式，能讓前綴依序保持合法，最後留下 `open` 個未配對左括號。
- `false`：目前沒有任何合法替換方式能到達這個狀態。

因此，這不是「第 `i` 個字元的答案」，而是「處理完前 `i` 個字元後，所有可能狀態的集合」。例如同一列同時有 `reachable[i, 0]` 與 `reachable[i, 2]` 為 `true`，代表同一個前綴可以透過不同的星號解釋，分別留下 0 或 2 個未配對左括號。

陣列大小是 `[length + 1, length + 1]`：

- 列索引 `0..length`：包含尚未處理任何字元的空前綴，以及完整字串。
- 欄索引 `0..length`：未配對左括號最多不會超過已處理字元數，因此 `length` 足以涵蓋所有可能值。
- `reachable[0, 0] = true`：空前綴不需要配對任何括號，是唯一的初始狀態。
- 其他格子預設為 `false`：尚未找到任何路徑可以到達它們。

可以把表格想成一張狀態圖：每一列是處理進度，每一欄是 `open` 數量；讀入一個字元，就從第 `i` 列走到第 `i + 1` 列。

### DP 表格如何對應程式

程式的兩層迴圈直接對應上面的表格：

```csharp
for (int processedLength = 0; processedLength < length; processedLength++)
{
    char character = s[processedLength];

    for (int openCount = 0; openCount <= length; openCount++)
    {
        if (!reachable[processedLength, openCount])
        {
            continue;
        }

        // 從這個可達狀態，依 character 寫入下一列。
    }
}
```

外層迴圈固定目前要消耗的字元，內層迴圈掃描這一列的每個 `openCount`。`continue` 很重要：不可達的格子不代表一條待嘗試的路徑，不能從它虛構新的狀態；只有 `true` 的格子才會向下一列轉移。

每次轉移都把結果寫到 `reachable[processedLength + 1, ...]`，因為目前字元已經被消耗。同一個下一格可能由多條路徑抵達，但布林值只需維持 `true` 一次，這就是 DP 合併重複子問題的地方。

### 三種字元的狀態轉移

若目前狀態是 `(i, open)`，處理字元後會前進到第 `i + 1` 列。以下只從已經可達的狀態開始：

#### `(`：未配對數量加一

真正的左括號沒有其他解釋，只能等待未來的右括號配對：

```text
(i, open) → (i + 1, open + 1)
```

因此程式執行：

```csharp
if (character == '(' || character == '*')
{
    reachable[processedLength + 1, openCount + 1] = true;
}
```

這個條件同時涵蓋星號視為左括號的分支；當 `character` 確實是 `(` 時，則只有這一條轉移。

#### `)`：未配對數量減一

真正的右括號必須消耗一個已存在的未配對左括號：

```text
(i, open) → (i + 1, open - 1)    （open > 0）
```

如果 `open == 0`，目前前綴沒有左括號可配對，不能讓數量變成 `-1`。這條路徑必須捨棄，而不是把負數保存到表格中。對應的程式是：

```csharp
if ((character == ')' || character == '*') && openCount > 0)
{
    reachable[processedLength + 1, openCount - 1] = true;
}
```

#### `*`：同時嘗試三種合法解釋

星號可以分別產生三條轉移：

| 星號解釋 | 狀態轉移 | 需要的條件 |
|---|---|---|
| 左括號 `(` | `(i, open) → (i + 1, open + 1)` | 沒有額外條件 |
| 空字串 | `(i, open) → (i + 1, open)` | 沒有額外條件 |
| 右括號 `)` | `(i, open) → (i + 1, open - 1)` | `open > 0` |

前兩條分別由第一個 `if` 與星號專用的區塊處理，第三條與真正的右括號共用最後一個 `if`：

```csharp
if (character == '*')
{
    // 星號視為空字串，openCount 維持不變。
    reachable[processedLength + 1, openCount] = true;
}
```

因此，星號不會被程式固定選成某一種角色，而是把三種可能都留下；後續字元再從這些狀態繼續轉移。若其中一條路徑變成負數，只有那一條被排除，其他仍合法的解釋不會受到影響。

### 為什麼不能保存負數狀態？

`open` 代表「手上還有多少個左括號等待配對」，本質上不可能是負數。負數不是另一種有效狀態，而是表示某個前綴已經出現沒有左括號可配對的右括號。

例如處理 `s = ")"` 時，初始狀態只有 `(0, 0)`。右括號若直接轉移，會得到 `open = -1`；但這代表錯誤的前綴 `)`，所以程式因 `openCount > 0` 不成立而不寫入任何狀態。最後一列沒有 `reachable[1, 0]`，答案自然是 `false`。

這個條件同時維持一個重要不變量：每個被保存的 `reachable[i, open]`，都代表前 `i` 個字元存在一條前綴始終合法的替換路徑。DP 不只檢查結尾數量相等，也在每次右括號出現時檢查順序是否正確。

### 範例演示：`(*))`

以下集合列出每個前綴可達的 `open`，並把每一步的來源展開：

| 已處理前綴 | 目前字元 | 前一列可達狀態 | 新增的狀態 | 處理後可達狀態 |
|---|:---:|---|---|---|
| 空字串 | — | — | `0`（初始狀態） | `{0}` |
| `(` | `(` | `{0}` | `0 → 1` | `{1}` |
| `(*` | `*` | `{1}` | `1 → 2`、`1 → 1`、`1 → 0` | `{0, 1, 2}` |
| `(*)` | `)` | `{0, 1, 2}` | `0` 被捨棄；`1 → 0`、`2 → 1` | `{0, 1}` |
| `(*))` | `)` | `{0, 1}` | `0` 被捨棄；`1 → 0` | `{0}` |

在 `(*` 這一列，星號分別視為右括號、空字串與左括號，所以同時留下 0、1、2 三種可能。處理下一個真正的右括號時，`open = 0` 的路徑不能再減一，只剩 `open = 1` 與 `open = 2` 可以繼續。

完整處理後仍有 `open = 0`，例如把星號當成左括號可得到 `(())`。因此 `reachable[4, 0]` 為 `true`，方法回傳 `true`。

### 提前失敗案例：`())*`

這個案例說明後面的星號不能挽救已經失效的前綴：

| 已處理前綴 | 可達的 `open` | 原因 |
|---|---|---|
| 空字串 | `{0}` | 初始狀態 |
| `(` | `{1}` | 左括號使數量加一 |
| `()` | `{0}` | 右括號完成配對 |
| `())` | `{}` | 沒有任何 `open > 0` 的狀態可供第三個字元配對 |
| `())*` | `{}` | 前一列沒有可達狀態，星號沒有路徑可以重新開始 |

目前的實作不需要在狀態集合變空時立即回傳；它會讓後續各列維持空集合，最後讀取 `reachable[length, 0]` 時得到 `false`。星號位於錯誤前綴之後，不能回到前面插入左括號，因此不能修復已經發生的順序錯誤。

### 正確性重點：狀態不變量

對每個 `i`，維持以下不變量：`reachable[i, open] == true` 恰好表示，前 `i` 個字元存在至少一種星號替換方式，使每個前綴都合法，並在第 `i` 個位置留下 `open` 個未配對左括號。

1. **初始成立**：`reachable[0, 0] = true`，空前綴合法且沒有未配對左括號；其他初始狀態都是 `false`。
2. **轉移保持成立**：程式只從可達狀態出發，且完整列出 `(`、`)` 與 `*` 的所有允許解釋。右括號只有在 `openCount > 0` 時才會消耗左括號，所以不會建立無效的負數狀態。
3. **不會漏解**：任何合法替換在讀取目前字元時，必定屬於上述某一條轉移，因此它的下一個狀態會被標記為 `true`。
4. **結尾判定正確**：完整字串處理後，只有 `open = 0` 代表所有左括號都已配對；所以 `reachable[length, 0]` 正好就是題目要判斷的答案。

### 複雜度

| 項目 | 複雜度 | 說明 |
|---|---:|---|
| 時間 | `O(n²)` | 外層處理 `n` 個字元，內層最多檢查 `n + 1` 個 `open` 狀態；每次轉移是 `O(1)`。 |
| 輔助空間 | `O(n²)` | 二維表保存所有前綴與未配對數量的可達性。 |

目前實作刻意保留完整二維表，方便直接觀察每個前綴的狀態。由於第 `i + 1` 列只依賴第 `i` 列，若只需要最後答案，日後可以改用兩列或一列把空間降為 `O(n)`；但那會失去完整保存所有前綴狀態的教學可讀性。

## 三種解法比較

| 解法 | 方法 | 時間 | 輔助空間 | 特色 |
|---|---|---:|---:|---|
| 雙索引堆疊 | `CheckValidString` | `O(n)` | `O(n)` | 保留實際位置，索引順序容易直接解釋 |
| 貪心上下界 | `CheckValidString2` | `O(n)` | `O(1)` | 將所有可能狀態壓縮成連續範圍，效率最佳 |
| 動態規劃 | `CheckValidString3` | `O(n²)` | `O(n²)` | 明確保存全部可達狀態，最適合理解完整選擇空間 |

若只考慮正式解題效率，貪心解法在時間與空間上最有優勢；雙堆疊解法適合強調括號位置順序；動態規劃則提供最直接、完整的狀態枚舉模型。
