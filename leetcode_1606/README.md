# 1606. Find Servers That Handled Most Number of Requests

# 找出處理最多請求的伺服器

使用 C# / .NET 10 實作兩種事件模擬解法，附可直接執行的範例與獨立正確性檢查。

[LeetCode 題目](https://leetcode.com/problems/find-servers-that-handled-most-number-of-requests/description/) · [解法一](#解法一有序集合與完成時間優先佇列) · [解法二](#解法二雙優先佇列與虛擬順位) · [執行方式](#建置與執行)

## 題目說明與限制

有 `k` 台編號為 `0..k-1` 的伺服器，每台同時只能處理一個請求。
第 `i` 個請求在 `arrival[i]` 到達，需處理 `load[i]` 時間：從 `i % k` 開始，依編號循環尋找第一台空閒伺服器；全部忙碌就丟棄。
回傳成功處理請求數最多的所有伺服器編號，順序不限。計算的是**請求數量**，不是總處理時間。

依[官方限制](https://leetcode.com/problems/find-servers-that-handled-most-number-of-requests/description/)：

- `1 <= k <= 100,000`。
- `1 <= arrival.Length == load.Length <= 100,000`。
- `1 <= arrival[i], load[i] <= 1,000,000,000`。
- `arrival` 嚴格遞增。

以下方法以符合題目限制的輸入為前提，不另外檢查 null、空陣列或長度不符。
完成時間為 `arrival[i] + load[i]`，最大 `2,000,000,000`，仍在 C# `int` 上限 `2,147,483,647` 內。
若伺服器完成時間恰好等於新請求到達時間，就能接新請求。

### 官方範例

| 範例 | k | arrival | load | 答案 |
| --- | --- | --- | --- | --- |
| 一 | 3 | `[1,2,3,4,5]` | `[5,2,3,3,3]` | `[1]` |
| 二 | 3 | `[1,2,3,4]` | `[1,2,1,2]` | `[0]` |
| 三 | 3 | `[1,2,3]` | `[10,12,11]` | `[0,1,2]` |

範例一前三個請求分配給 0、1、2。第四個請求到達時，只有伺服器 1 已完成，故由它處理；第五個請求到達時全部忙碌而丟棄，最終次數為 `[1,2,1]`。

## 解題概念與出發點

最直接的方法是用陣列記錄每台伺服器的完成時間。每個請求從 `i % k` 開始，最多掃描 `k` 台，找到完成時間不晚於到達時間的第一台就分派。
這是容易驗證的 O(nk) 模擬，但 `n` 與 `k` 都可能達十萬，最壞需要約一百億次檢查。
本專案只在小型隨機檢查的 `BruteForce` 使用這個方式作為獨立基準。

兩種正式解法都將問題拆成兩件事：

1. **哪些伺服器剛完成？** 用最小優先佇列 `busy`，以完成時間為優先值，只處理已完成的項目。
2. **從指定編號開始，下一台空閒的是誰？** 解法一直接查有序集合；解法二將循環順序轉成線性順位後取最小值。

不必逐時間單位模擬，只在每個請求到達時更新狀態。每台伺服器恰好存在於空閒或忙碌容器之一，避免重複分派。
即使請求丟棄，`i` 仍代表原始輸入索引，下一個起點不能改用已接受請求的數量。

### 先分清楚兩條軸：請求索引與實際時間

`i` 決定「從哪台開始找」，`arrival[i]` 決定「哪些伺服器已完成」。這兩個數值用途不同，不能互相替換。
以官方範例一為例：

```text
request index i :   0       1       2       3       4
arrival[i]     :   1       2       3       4       5
i % 3          :   0       1       2       0       1
assigned server:   0       1       2       1       X (drop)
```

這個範例剛好每隔一個時間單位到達，但輸入也可以是 `[1,10,100]`。
即使時間跳了很大一段，起點仍依序為 0、1、2；只需要在下一次到達時，一次釋放所有已完成的伺服器。

### 共同流程 ASCII 圖

```text
                 request i arrives at time t
                              |
                              v
             +--------------------------------+
             | while busy.min.finishTime <= t |
             |   pop completed server         |
             |   add to available             |
             | repeat until false / empty     |
             +--------------------------------+
                              |
                              v
                   available is empty ?
                     | yes           | no
                     v               v
                   DROP        choose next server
                     |         from target = i % k
                     |               |
                     |               v
                     |         requests[id] += 1
                     |         remove from available
                     |         busy.push(t + load[i], id)
                     |               |
                     +-------+-------+
                             v
                          i = i + 1
```

釋放迴圈會重新檢查堆積頂端，直到最早的完成時間也大於 `t`，才往下進行。
`busy` 依完成時間排序，因此頂端還沒完成時，其他忙碌項目也一定沒完成，不需要掃描整個佇列。
若多台同時完成，它們的取出順序不重要：分派前會先全部放回空閒容器。

## 解法一：有序集合與完成時間優先佇列

對應 `BusiestServers(int k, int[] arrival, int[] load)`，回傳 `IList<int>`。

### 資料結構與初始化

| 狀態 | 結構 | 用途 |
| --- | --- | --- |
| `available` | `SortedSet<int>` | 儲存所有空閒編號，依編號排序；初始加入 `0..k-1` |
| `busy` | `PriorityQueue<(int finishTime, int server), int>` | 元素記錄完成時間與編號，優先值是完成時間；初始為空 |
| `requests` | `int[k]` | 各伺服器成功接收請求的次數；初始為零 |

#### `SortedSet<int>` 是什麼？

```csharp
SortedSet<int> available = new SortedSet<int>();
```

這行建立一個空集合，命名為 `available`，用來保存目前空閒的伺服器編號。名稱可以拆開理解：

| 部分 | 意義 |
| --- | --- |
| `Sorted` | 元素會自動排序；這裡的整數預設由小到大排列 |
| `Set` | 集合，不允許重複元素 |
| `<int>` | 元素的型別是整數 |
| `new SortedSet<int>()` | 建立一個新的空集合物件 |

以下獨立範例刻意打亂加入順序，並重複加入 2：

```csharp
SortedSet<int> available = new SortedSet<int>();
available.Add(4);
available.Add(0);
available.Add(2);
available.Add(2); // 已經有 2，不會重複加入。

Console.WriteLine(string.Join(", ", available)); // 0, 2, 4
```

因此集合內容是 `{0,2,4}`。下表各列都以這個集合為操作前的狀態：

| 操作 | 結果與本題用途 |
| --- | --- |
| `available.Add(1)` | 加入後為 `{0,1,2,4}`；伺服器完成工作時放回空閒集合 |
| `available.Remove(2)` | 移除後為 `{0,4}`；伺服器接下工作時移出空閒集合 |
| `available.Min` | 取得最小空閒編號 0，不移除元素 |
| `available.Max` | 取得最大空閒編號 4，不移除元素 |
| `available.Count` | 取得空閒伺服器數量 3 |

`SortedSet<int>` 不支援用 `available[0]` 依索引取得第一個元素；這裡要取得最小編號應使用 `available.Min`。
相較之下，`List<int>` 支援索引與重複元素，但加入元素時不會自動排序。本題選擇 `SortedSet<int>`，是為了在伺服器持續加入、移除時，仍能依編號快速尋找下一台空閒伺服器。

正式程式會用 `for` 逐一加入 `0..k-1`。例如 `k=3`，初始狀態為：

```text
available = {0,1,2}
busy      = 空
requests  = [0,0,0]
```

#### `busy` 的元素與優先值

```csharp
PriorityQueue<(int finishTime, int server), int> busy = new PriorityQueue<(int, int), int>(
    Comparer<int>.Create((a, b) => a.CompareTo(b)));
```

`PriorityQueue<TElement, TPriority>` 的第一個型別代表「儲存的元素」，第二個型別代表「決定取出順序的優先值」：

- 元素 `(int finishTime, int server)` 同時記錄完成時間與伺服器編號。
- 優先值 `int` 在每次入列時指定為完成時間。
- `a.CompareTo(b)` 依整數由小到大比較，讓完成時間較小的項目先取出；這也等同 `int` 的預設比較順序。

例如 `busy.Enqueue((6, 0), 6)` 表示「伺服器 0 將在時間 6 完成」，並以 6 作為優先值。
因此佇列頂端是最早完成的項目，並非編號最小或最早加入的伺服器。

### 每個請求的處理步驟

1. 持續取出 `busy` 中 `finishTime <= arrival[i]` 的元素，將伺服器加入 `available`。必須使用 `while`，因為可能有多台同時完成。
2. 若 `available.Count == 0`，丟棄目前請求。
3. 令 `target = i % k`，選擇不小於 `target` 的最小空閒編號；如果所有空閒編號都小於它，就繞回最小編號。
4. 次數加一，以 `arrival[i] + load[i]` 作為完成時間加入 `busy`，再將選中的編號移出空閒集合。
5. 全部請求處理完後，求最大次數並收集所有相等的編號。

### 逐行理解：釋放所有已完成的伺服器

```csharp
while (busy.Count > 0 && busy.Peek().finishTime <= arrival[i])
{
    var item = busy.Dequeue();
    available.Add(item.server);
}
```

這段可以讀成：「只要忙碌佇列不為空，而且最早的完成時間不晚於目前請求到達時間，就將那台伺服器移回空閒集合，接著繼續檢查下一台。」

| 程式 | 意義 |
| --- | --- |
| `busy.Count > 0` | 先確認佇列還有項目 |
| `&&` | 左邊成立才計算右邊；若佇列為空，就不會呼叫 `Peek()`，避免空佇列存取錯誤 |
| `busy.Peek()` | 查看最早完成的元素，但不移除它 |
| `.finishTime <= arrival[i]` | 判斷這台伺服器是否已在新請求到達前或到達當下完成 |
| `busy.Dequeue()` | 移除最早完成的元素，並將它回傳給 `item`；`var` 讓編譯器推斷其型別為完成時間與編號的 tuple |
| `available.Add(item.server)` | 取出該元素中的伺服器編號，加入空閒集合 |

假設新請求在時間 6 到達，原本沒有空閒伺服器，而 `busy` 的取出順序為 `(4,1)、(6,0)、(9,2)`；每一組是 `(完成時間, 伺服器編號)`：

| 檢查頂端 | 條件 | 動作 | 動作後的 `available` |
| --- | --- | --- | --- |
| `(4,1)` | `4 <= 6` 成立 | 移除項目，釋放伺服器 1 | `{1}` |
| `(6,0)` | `6 <= 6` 成立 | 移除項目，釋放伺服器 0 | `{0,1}` |
| `(9,2)` | `9 <= 6` 不成立 | 停止迴圈，項目留在 `busy` | `{0,1}` |

使用 `<=`，是因為時間 6 完成的工作不會占用時間 6 新到達的請求所需的處理時段。
使用 `while` 而非 `if`，則是為了在分派前釋放**所有**已完成的伺服器；這個例子若只釋放一台，就會漏掉已空閒的伺服器 0。

### 沒有空閒伺服器時，丟棄目前請求

```csharp
if (available.Count == 0)
{
    continue;
}
```

必須先釋放已完成的伺服器，再判斷集合是否為空，才能使用剛完成工作的伺服器。
若釋放後仍為空，`continue` 會跳過本輪分派與計數，但外層 `for` 仍會執行 `i++`。
例如 `k=3`、索引 `i=2` 的請求被丟棄後，下一個索引仍是 `i=3`，搜尋起點為 `3 % 3 = 0`；不能改用成功接收的請求數計算起點。

### 如何快速找下一台

先決定搜尋起點，再決定實際分派對象：

```csharp
int target = i % k;
int serverId = available.Max < target
    ? available.Min
    : available.GetViewBetween(target, k - 1).Min;
```

`%` 是取餘數。假設 `k=6`，請求索引 `i=3、5、8` 時，`target` 分別為 `3、5、2`。
**`target` 只是從哪個編號開始找，不保證該伺服器空閒；`serverId` 才是最後選中的空閒伺服器。**

三元運算式 `條件 ? 成立時的值 : 不成立時的值`，可改寫成完全等價的 `if / else`，較容易分開閱讀：

```csharp
int target = i % k;
int serverId;

if (available.Max < target)
{
    // 連最大的空閒編號都小於起點，後面沒有可選對象，必須繞回。
    serverId = available.Min;
}
else
{
    // 起點或後面還有空閒伺服器，選其中編號最小的。
    serverId = available.GetViewBetween(target, k - 1).Min;
}
```

以下三種情況都固定使用 `k=6`、`available={0,2,4}`，也就是編號 0、2、4 空閒，1、3、5 忙碌：

| `target` | 依題意搜尋的順序 | `available.Max < target` | 查找方式 | `serverId` |
| --- | --- | --- | --- | --- |
| 2 | `2 → 3 → 4 → 5 → 0 → 1` | `4 < 2` 不成立 | 區間 `[2,5]` 有 `{2,4}`，取最小值 | 2 |
| 3 | `3 → 4 → 5 → 0 → 1 → 2` | `4 < 3` 不成立 | 區間 `[3,5]` 只有 `{4}`，取最小值 | 4 |
| 5 | `5 → 0 → 1 → 2 → 3 → 4` | `4 < 5` 成立 | 起點後方沒有空閒編號，繞回取全體最小值 | 0 |

以 `target=3` 展開 `available.GetViewBetween(3, 5).Min`：

1. `GetViewBetween(3, 5)` 取得編號介於 3 到 5 的集合視圖，**包含上下界**；這裡視圖中只有 `{4}`。
2. 視圖連結到原集合，並非另外複製一份集合；此處僅讀取，不修改內容。
3. `.Min` 取得該範圍內最小的空閒編號，因此選 4。

若 `target=2`，因為範圍包含下界，所以可以直接選到空閒的起點 2。
若 `target=5`，最大空閒編號才到 4，代表 `[5,5]` 沒有空閒伺服器，必須繞回選 0。
也不能每次一律取 `available.Min`：從 3 開始搜尋時會先遇到 4，雖然 0 也空閒，仍必須等繞回後才輪到它。

前面已排除空集合。當 `available.Max >= target` 時，區間內必定有元素，所以能安全取 `Min`。
這個查找相當於 ceiling（大於等於目標的最小值），不需要從最小編號逐一走訪。

在 [.NET 10 的 TreeSubSet 原始碼](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Collections/src/System/Collections/Generic/SortedSet.TreeSubSet.cs)中，區間定位與最小值查找沿樹路徑進行；區間 `Count` 則可能觸發重新走訪計數。
因此這裡直接依母集合的 `Max` 判斷是否需要繞回，避免以區間視圖的 `Count` 判斷有無後繼。母集合的 `available.Count` 不屬於這個問題。

### ASCII 圖：把循環搜尋拆成兩段

以 `k=6`、空閒編號 `{0,2,4}` 為例。`F` 表示空閒，`B` 表示忙碌。
圖中的編號列是邏輯順序，不是 `SortedSet` 的內部樹形。

```text
server:     0   1   2   3   4   5
state :     F   B   F   B   F   B

case A: target = 3
search:                 3 ->4 ->5 | 0 ->1 ->2
                            ^
                            first free = 4

        [target .. k-1] = [3 .. 5]
        available in this range = {4}
        choose range.Min = 4

case B: target = 5
search:                         5 | 0 ->1 ->2 ->3 ->4
                                    ^
                                    first free = 0

        [target .. k-1] = [5 .. 5]
        available in this range = {}
        wrap around -> choose available.Min = 0
```

循環順序其實就是先查 `[target,k-1]`，再查 `[0,target-1]`。
只要右半段有空閒編號，左半段再小也不能優先選；右半段完全沒有空閒時，才繞回。
這正是「找後繼，找不到就取全體最小值」的由來。

### 分派成功後，更新次數與忙碌狀態

```csharp
requests[serverId]++;
busy.Enqueue((arrival[i] + load[i], serverId), arrival[i] + load[i]);
available.Remove(serverId);
```

這三行依序完成：

1. 該伺服器成功接收的請求數加一；比較的是請求數量，不是累計負載。
2. 計算新完成時間，以 `(完成時間, 編號)` 作為元素、完成時間作為優先值加入 `busy`。
3. 將該編號移出 `available`，避免同一台伺服器同時接到另一個請求。

例如 `serverId=1`、`arrival[i]=4`、`load[i]=3`，就會將 `requests[1]` 加一，執行 `busy.Enqueue((7, 1), 7)`，並從空閒集合移除 1。
完成時間是 `4+3=7`，因為成功分派的請求會在到達時立即開始處理，沒有等待佇列。

### ASCII 圖：完成時間佇列與集合如何交接

以下放大官方範例一的第 3 輪。圖中 `busy` 按完成時間展開，表示取出順序，並非實際堆積陣列布局。
`(finish,id)` 代表完成時間與伺服器編號。

```text
i = 3, t = arrival[3] = 4, load[3] = 3, target = 0

BEFORE release:
    busy      : [(4,1), (6,0), (6,2)]
    available : {}
    requests  : [1,1,1]

    (4,1) -- finish <= t --> release server 1
    (6,0) -- finish >  t --> stop releasing

AFTER release:
    busy      : [(6,0), (6,2)]
    available : {1}
                     target 0 -> next free 1

ASSIGN server 1:
    available : {1} -- remove 1 --> {}
    busy      : [(6,0), (6,2)] -- push (4+3,1) --> [(6,0), (6,2), (7,1)]
    requests  : [1,1,1] -- count server 1 --> [1,2,1]
```

下一輪 `i=4, t=5` 時，最早完成時間是 6，所以沒有伺服器可釋放；空閒集合仍為空，該請求便丟棄。
伺服器 1 的完成時間會從 4 更新成 7，因為它接到的是一個新請求。

### 逐步演示：官方範例一

`k = 3, arrival = [1,2,3,4,5], load = [5,2,3,3,3]`。
空閒集合列的是本輪釋放後、分派前的狀態；次數列的是分派後的狀態。

| i | 到達 / 負載 | 本輪釋放 | 空閒集合 | target | 選擇與完成時間 | 次數 `[0,1,2]` |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 1 / 5 | 無 | `{0,1,2}` | 0 | 0，完成於 6 | `[1,0,0]` |
| 1 | 2 / 2 | 無 | `{1,2}` | 1 | 1，完成於 4 | `[1,1,0]` |
| 2 | 3 / 3 | 無 | `{2}` | 2 | 2，完成於 6 | `[1,1,1]` |
| 3 | 4 / 3 | 1 | `{1}` | 0 | 後繼為 1，完成於 7 | `[1,2,1]` |
| 4 | 5 / 3 | 無 | `{}` | 1 | 丟棄 | `[1,2,1]` |

### 收集全部並列最多的伺服器

```csharp
int maxRequests = requests.Max();
List<int> result = new List<int>();
for (int i = 0; i < k; i++)
{
    if (requests[i] == maxRequests)
    {
        result.Add(i);
    }
}
return result;
```

`requests.Max()` 先求出最多的請求數，再逐台檢查，將所有達到該次數的編號加入結果。
例如 `requests=[3,1,3,2]`，最大值是 3，編號 0、2 都達到最大值，所以回傳 `[0,2]`，不能只保留第一台。
官方範例一的次數為 `[1,2,1]`，因此回傳 `[1]`。

實際建立的是 `List<int>`；因為它實作 `IList<int>` 介面，所以可以作為此方法的回傳值。
請求分派成功時就已計數，後續完成事件不會改變次數，因此全部請求分派完後，不必再清空 `busy` 或模擬到最後一台完成。

### 正確性與複雜度

釋放後，`available` 恰好包含到達時間已空閒的全部伺服器：已完成的項目全部取出，尚未完成的項目留在 `busy`。
有序集合從 `target` 向右取最小值，右側無解才取全體最小值，恰好符合題目的循環順序。
每次只更新被選中的伺服器，因此可逐請求歸納出分派與次數都正確；最後取全部最大值便得到答案。

初始化逐一插入 `k` 個編號需要 O(k log k)。每個請求最多加入忙碌佇列一次，其後最多取出一次，所有釋放操作合計 O(n log k)，不是每個請求都額外釋放 `k` 次。
包含查找、集合更新與最後掃描，總時間為 **O((n+k) log k)**；`k = 1` 時為 O(n)。統一寫法可用 O((n+k) log(k+1))。
兩個容器合計最多 `k` 台伺服器，額外空間 **O(k)**，答案最多也有 `k` 個編號。

## 解法二：雙優先佇列與虛擬順位

對應 `BusiestServers2(int k, int[] arrival, int[] load)`，同樣回傳 `IList<int>`。

`busy` 與次數陣列的用途和解法一相同；`available` 改用 `PriorityQueue<int,int>`：
元素是實際伺服器編號，優先值是虛擬順位 `pos`。初始化把編號 `id` 以順位 `id` 加入。

### 資料結構與初始化

| 狀態 | 型別 | 元素或內容 | 優先值 | 初始化 | `Dequeue()` 回傳 |
| --- | --- | --- | --- | --- | --- |
| `available` | `PriorityQueue<int, int>` | 實際伺服器編號 `id` | 虛擬順位 `pos`，越小越先選 | 將 `0..k-1` 逐一以自身編號作為順位入列 | 實際編號 `id` |
| `busy` | `PriorityQueue<(int finishTime, int server), int>` | `(完成時間, 伺服器編號)` | 完成時間，越小越早釋放 | 空佇列 | 整個 `(finishTime, server)` tuple |
| `requests` | `int[k]` | 每台成功接收的請求數 | 不適用 | 全部為零 | 不適用 |

`PriorityQueue<TElement, TPriority>` 的兩個型別參數分別代表元素與優先值；即使兩者都是 `int`，用途仍然不同。
`Enqueue(element, priority)` 同時指定兩者，`Peek()` 與 `Dequeue()` 則只回傳元素：前者查看但不移除，後者取出並移除優先值最小的項目。

例如 `available.Enqueue(0, 6)` 儲存的是「編號 0、順位 6」；若它是頂端，`available.Dequeue()` 回傳 0。
`busy.Enqueue((7, 0), 7)` 則表示「編號 0 在時間 7 完成」，取出時回傳 `(7, 0)`。
因此 `id` 回答「是哪台」、`pos` 回答「搜尋時排第幾個虛擬位置」、`finishTime` 回答「何時完成」；順位不代表實際時間。

### 為什麼不能直接依編號使用最小堆積

若空閒編號為 `{0,2}`、本輪起點是 1，應選 2，直接取最小編號卻會得到 0。
真正需要排序的是「從本輪起點沿循環方向走多少步」，而不是原始編號。

把循環攤開成無限的線性序列（以 `k = 3` 為例）：

```text
虛擬位置：0 1 2 | 3 4 5 | 6 7 8 | ...
實際編號：0 1 2 | 0 1 2 | 0 1 2 | ...
```

第 `i` 輪從虛擬位置 `i` 開始；對伺服器 `id`，需要第一個不小於 `i` 且與 `id` 模 `k` 同餘的位置。

### ASCII 圖：用一段長度 k 的視窗看循環順序

仍以 `k=3` 為例，第 `i=4` 輪的起點是編號 `4 % 3 = 1`。
只看虛擬位置 `[4,6]`，就剛好包含每個編號一次，而且順序正好是 1、2、0。

```text
virtual position:   0  1  2 | 3  4  5 | 6  7  8
server id       :   0  1  2 | 0  1  2 | 0  1  2
                                [-------]
window [i,i+k-1]:                4  5    6
cyclic order    :                1  2    0
                                ^
                                start at i = 4
```

假設此時編號 0、2 空閒，編號 1 忙碌：

```text
id             :    1       2       0
state          :    B       F       F
distance       :    0       1       2
priority (pos) :    4       5       6
                            ^
                            minimum available priority
                            choose id 2

available entries (element=id, priority=pos):
    [(id=2, pos=5), (id=0, pos=6)]
       |
       +-- Dequeue() returns 2
```

雖然編號 0 比 2 小，但順位 6 比 5 大，所以會正確選到 2。
這個視窗是理解排序的工具，程式不會真的建立無限序列，也不會建立長度 `k` 的視窗陣列；它只替空閒伺服器儲存一個順位整數。

### 推導釋放時的順位公式

先沿用解法一的搜尋起點 `target = i % k`，計算從起點沿循環方向走到 `id` 所需的步數：

```csharp
int target = i % k;
int distance = (id - target + k) % k;
int pos = i + distance;
```

`id` 與 `target` 都在 `[0,k-1]`，所以 `id-target` 介於 `-(k-1)` 與 `k-1`；加上 `k` 後再取餘數，就能得到 `[0,k-1]` 的向前距離。
若 `id == target`，距離為 0；若 `id < target`，則需要繞回。例如 `k=3, i=4` 時，`target=1`：到編號 1、2、0 分別走 0、1、2 步，順位便是 4、5、6。

這裡加回的是虛擬起點 `i`，讓順位保留在同一條持續前進的位置軸上；`target` 只用來計算本輪的循環距離。
由於 `i` 與 `i % k` 相差整數倍的 `k`，`id-i` 與 `id-target` 正規化後會得到相同的模 `k` 餘數。
因此實際程式可以直接使用 `i`，寫成下列等價公式；這是原始順位運算拆成兩行的教學寫法：

```csharp
int distance = ((id - i) % k + k) % k;
int pos = i + distance;
```

使用 `id-i` 時，差值可能小於 `-k`，所以先 `% k`，再加 `k`、取餘數；不能直接將上一段改成 `(id-i+k)%k`，否則仍可能得到負值。

- `id - i` 表示相對於本輪起點的偏移。
- C# 的 `%` 是餘數運算，負數可能產生負餘數；先加 `k` 再取餘數，將距離正規化到 `[0,k-1]`。
- 加回 `i` 後，`pos` 位於 `[i,i+k-1]`，且 `pos % k == id`。
- 因此取最小 `pos`，就是取從本輪起點最先遇到的空閒編號。

例如 `k=3, i=4, id=0`：`id-i=-4`，C# 中 `-4 % 3 = -1`，修正後距離為 2，所以 `pos=6`。
這代表本輪從編號 1 開始，經過 1、2 後才到 0。
順位上界為 `(n-1)+(k-1) <= 199,998`，同樣可使用 `int`。

### 把公式逐步算一次

設定 `k=3, i=4`。下表是各編號**若在本輪釋放**時要使用的順位；忙碌而未完成的編號不會加入空閒佇列。

| id | id - i | C# `(id-i) % k` | 加 k 再取餘數得到 distance | pos = i + distance |
| --- | --- | --- | --- | --- |
| 0 | -4 | -1 | `(-1+3)%3 = 2` | 6 |
| 1 | -3 | 0 | `(0+3)%3 = 0` | 4 |
| 2 | -2 | -2 | `(-2+3)%3 = 1` | 5 |

因此順位遞增的順序是 `id=1 -> id=2 -> id=0`，剛好是本輪需要的循環順序。
這也說明不能直接使用 `(id-i)%k`：編號 0、2 的距離會是負數，失去「向前走幾步」的意義。

`pos` 加上 `i` 也有用途：不同輪釋放的伺服器需要使用同一條虛擬位置軸。
如果僅存當輪算出的 `distance`，舊項目的相對距離會隨起點移動而失效；儲存絕對位置 `pos`，搭配每輪取走最小值，才能安全保留舊項目。

### 為什麼舊的空閒順位不用每輪更新

可以先把 `i` 想成沿虛擬位置軸前進的指標：**每輪起點只前進一格；如果某個空閒順位正好是即將越過的 `i`，它一定會先被取走。**
因為本輪沒有小於 `i` 的合法順位，順位 `i` 若存在，就必定在堆積頂端；若選到大於 `i` 的順位，代表沒有順位 `i` 留在佇列裡。
若請求丟棄，則空閒佇列為空，同樣沒有過期項目。到達時間即使大幅跳躍，下一個請求索引仍只是 `i+1`，不會一次越過多個虛擬位置。
以下用不變量說明：為什麼上述「本輪沒有小於 `i` 的順位」能從初始化一路維持下去。

關鍵不變量是：**第 `i` 輪釋放完畢後，每個空閒伺服器的順位都位於 `[i,i+k-1]`，且順位模 `k` 等於編號。**

1. 初始 `i=0` 時，各順位為 `0..k-1`，成立。
2. 本輪新釋放的伺服器依公式加入，順位必定落在該區間。
3. 同一台伺服器不會重複存在於空閒佇列；不同編號的順位也不會相等，因為它們模 `k` 的餘數不同。
4. 若有順位恰好為 `i`，它必然是最小值而被取出；如果沒有，所有留下的順位本來就大於 `i`。
5. 下一輪既有順位都至少為 `i+1`，上界仍不超過下一輪的上界 `i+k`，因此仍是各編號最早的合法位置。若本輪丟棄，佇列為空，也沒有過期順位留下。

所以只需要在伺服器「從忙碌變空閒」時計算一次順位，不能將每輪更新整個堆積當成必要步驟。

### ASCII 圖：留下的順位為什麼不會過期

先看 `k=3, arrival=[1,2,3,4], load=[1,2,1,2]`，這是官方範例二。
以下 `id:pos` 代表「元素是編號、優先值是順位」，不是完成時間。

```text
i=0, t=1, window=[0,2]
    available before assignment: [0:0, 1:1, 2:2]
    choose 0:0  --> remaining:   [1:1, 2:2]
                                 ^ both positions >= 1

i=1, t=2, window=[1,3]
    server 0 finishes at t=2
    reinsert 0 with pos=1+2=3
    available before assignment: [1:1, 2:2, 0:3]
    choose 1:1  --> remaining:   [2:2, 0:3]
                                 ^ both positions >= 2

i=2, t=3, window=[2,4]
    no release
    available before assignment: [2:2, 0:3]
    choose 2:2  --> remaining:   [0:3]
                                 ^ position >= 3

i=3, t=4, window=[3,5]
    servers 1 and 2 finish at t=4
    reinsert 1 with pos=4, 2 with pos=5
    available before assignment: [0:3, 1:4, 2:5]
    choose 0:3
```

注意伺服器 0 在第 1 輪以順位 3 放回後，第 2 輪仍然保留順位 3，直到第 3 輪才被選中。
它不需要改成新的順位，因為本輪的起點還沒越過位置 3；等起點真的走到 3 時，它會是最小值並被取出。
若某輪跳過起點順位、選到更大的順位，也代表佇列中本來就沒有較小的順位，所以同樣不會留下已過期的項目。

這個性質依賴每輪最多移動一個請求索引 `i`，而不是依時間跳躍。
例如從 `arrival[i]=3` 跳到下一個到達時間 100，虛擬起點仍只從 `i` 變成 `i+1`；完成時間佇列負責處理這段期間所有完成的請求。

### 每個請求的處理步驟

1. 從 `busy` 釋放所有 `finishTime <= arrival[i]` 的伺服器，以本輪公式計算 `pos` 後加入 `available`。
2. 若 `available` 為空，丟棄請求；否則取出最小優先值所對應的實際編號。
3. 次數加一，計算新完成時間並放入 `busy`。
4. 結束後收集次數等於最大值的所有編號。

### 逐行理解：釋放並計算空閒順位

以下片段保留實作中的運算，省略程式註解以便對照：

```csharp
while (busy.Count > 0 && busy.Peek().finishTime <= arrival[i])
{
    var (_, id) = busy.Dequeue();
    int pos = i + ((id - i) % k + k) % k;
    available.Enqueue(id, pos);
}
```

| 程式 | 意義 |
| --- | --- |
| `busy.Count > 0 && ...` | 先確認佇列非空；`&&` 的短路判斷避免對空佇列呼叫 `Peek()` |
| `busy.Peek().finishTime <= arrival[i]` | 查看最早完成時間，判斷是否已可釋放；剛好等於到達時間也能接新請求 |
| `var (_, id) = busy.Dequeue()` | 取出並移除最早完成的 tuple，以解構方式將第二個欄位存入 `id`；`_` 表示捨棄已完成判斷用途的時間欄位 |
| `int pos = i + ((id - i) % k + k) % k` | 使用本輪索引重新計算該伺服器最早的合法虛擬順位，不沿用上一次接單前的順位 |
| `available.Enqueue(id, pos)` | 將實際編號作為元素、順位作為優先值，放回空閒佇列 |

例如 `k=3, i=4` 時釋放編號 0，就會算出 `pos=6`，執行 `available.Enqueue(0, 6)`。
迴圈持續處理所有已完成的伺服器，讓它們都能參與本輪分派；這和解法一使用 `while` 的理由相同。

### 逐行理解：丟棄或分派請求

```csharp
if (available.Count == 0)
{
    continue;
}

int serverId = available.Dequeue() % k;
requests[serverId]++;
busy.Enqueue((arrival[i] + load[i], serverId), arrival[i] + load[i]);
```

| 程式 | 意義 |
| --- | --- |
| `available.Count == 0` | 在釋放完畢後檢查是否仍無空閒伺服器 |
| `continue` | 丟棄目前請求，跳過分派與計數；外層 `for` 仍執行 `i++` |
| `available.Dequeue()` | 選擇順位最小的項目，回傳實際編號，並同時將它從空閒佇列移除 |
| `% k` | 元素已是 `[0,k-1]` 的實際編號，所以此處取餘數不改變結果；循環順序由入列時的 `pos` 決定 |
| `requests[serverId]++` | 將選中伺服器成功接收的請求數加一 |
| `busy.Enqueue(...)` | 以 `(完成時間, 編號)` 作為元素、`arrival[i]+load[i]` 作為優先值，記錄新工作 |

例如空閒項目依順位為 `(id=2, pos=5)`、`(id=0, pos=6)`，`Dequeue()` 回傳 2，且取出後只剩編號 0。
因此不必像解法一在選取後另外呼叫 `Remove(serverId)`；被選中的伺服器已離開空閒佇列，接著進入忙碌佇列。
請求分派成功時立即開始工作，所以完成時間從本輪 `arrival[i]` 加上負載計算，與虛擬順位無關。

### 逐步演示：官方範例一

使用與解法一相同的輸入。`編號:順位` 按優先值排序顯示，方便閱讀；不代表堆積內部實際排列。

| i | 到達 / 負載 | 本輪釋放與順位計算 | 空閒 `編號:順位` | 選擇與完成時間 | 次數 `[0,1,2]` |
| --- | --- | --- | --- | --- | --- |
| 0 | 1 / 5 | 無，初始順位 0、1、2 | `0:0, 1:1, 2:2` | 0，完成於 6 | `[1,0,0]` |

### ASCII 圖：同一台伺服器在兩個佇列間移動

以官方範例一 `i=3, t=4` 為例，伺服器 1 的上一個請求剛完成。

```text
busy ordered by finish time        available ordered by virtual position

[(4,1), (6,0), (6,2)]              []
   |
   +-- release id=1
       pos = 3 + ((1-3)%3+3)%3
           = 3 + 1 = 4
                     --------------------> [id=1, pos=4]
                                                |
                                      Dequeue() returns id=1
                                                |
[(6,0), (6,2), (7,1)] <--------------------------+
                  finish = arrival[3] + load[3] = 4 + 3 = 7
```

兩個佇列的優先值回答不同問題：完成時間 4 告訴我們「現在能釋放」，虛擬順位 4 告訴我們「現在應先選誰」。
此例兩者碰巧都是 4，沒有必須相等的關係；新完成時間是 7，也不會拿來當空閒順位。

### 正確性與複雜度

完成時間佇列保證空閒狀態正確；上述順位不變量保證最小順位就是循環順序的第一台。
兩者合起來，每輪選擇都符合題意，後續計數與最大值收集自然得到同一答案。

目前初始化逐一入列 `k` 台，每個請求與每次完成最多各操作固定次數的堆積。
總時間 **O((n+k) log k)**，`k=1` 時 O(n)，也可統一寫成 O((n+k) log(k+1))；額外空間 **O(k)**。

| i | 到達 | 可用編號 | target | 結果 | 次數 |
| --- | --- | --- | --- | --- | --- |
| 0 | 1 | `{0,1}` | 0 | 選 0，完成於 11 | `[1,0]` |
| 1 | 2 | `{1}` | 1 | 選 1，完成於 12 | `[1,1]` |
| 2 | 3 | 空 | 0 | 丟棄 | `[1,1]` |
| 3 | 11 | `{0}` | 1 | 繞回選 0，完成於 12 | `[2,1]` |

丟棄之後第 3 個索引仍是 `i=3`，所以起點是 1。解法二在此釋放 0 時，`pos=3+1=4`，同樣能選到 0。

## 解法比較

| 項目 | 解法一 | 解法二 |
| --- | --- | --- |
| 空閒容器 | 有序集合 | 最小優先佇列 |
| 選擇方式 | 後繼查找，無後繼則取最小編號 | 取虛擬順位最小的編號 |
| 理解重點 | 循環區間與集合查找 | 公式、負餘數及順位不變量 |
| 時間（目前初始化方式） | O((n+k) log k) | O((n+k) log k) |
| 額外空間 | O(k) | O(k) |
| 適合閱讀順序 | 先讀，直觀對應題意 | 再讀，理解如何將循環轉成線性順序 |

兩者都不需要在全部請求處理完後再清空 `busy`：請求分派成功時已計數，後續完成順序不會改變答案。
