## 題目與限制

題目來源：[LeetCode 2747](https://leetcode.com/problems/count-zero-request-servers/description/)／[中文題目](https://leetcode.cn/problems/count-zero-request-servers/description/)。更細的題意入門可參閱 [題目說明.md](題目說明.md)。

給定 `n` 台伺服器，編號為 `1` 到 `n`。`logs[i] = [server_id, time]` 表示某台伺服器在指定時間收到一次請求。另給定視窗寬度 `x` 和查詢時間陣列 `queries`。

對每個查詢時間 `q`，計算在閉區間 `[q - x, q]` 內**完全沒有收到請求的伺服器數量**。答案必須按照輸入查詢的原始順序回傳。

左右端點都算在內；同一台伺服器收到多次請求，也只算一台活躍伺服器。某台即使曾經收到請求，只要該請求在本次區間外，本次仍可能是零請求。

| 輸入 | 限制 |
|---|---|
| `n` | `1 <= n <= 100000` |
| `logs.Length` | `1 <= logs.Length <= 100000` |
| `logs[i].Length` | 恰為 `2` |
| `logs[i][0]` | `1 <= server_id <= n` |
| `logs[i][1]` | `1 <= time <= 1000000` |
| `x` | `1 <= x <= 100000` |
| `queries.Length` | `1 <= queries.Length <= 100000` |
| `queries[i]` | `x < queries[i] <= 1000000` |

程式以合法題目輸入為前提，不另外驗證空陣列、空值或範圍外資料。

### 官方範例

```text
範例一
n = 3
logs = [[1,3],[2,6],[1,5]]
x = 5
queries = [10,11]
答案 = [1,2]

範例二
n = 3
logs = [[2,4],[2,1],[1,2],[3,1]]
x = 2
queries = [3,4]
答案 = [0,1]
```

範例二的 `[1,3]` 有伺服器 1、2、3 活躍，答案為 `0`；`[2,4]` 只剩 1、2 活躍，答案為 `1`。

## 解題出發點

直接逐台檢查是否沒有請求，需要反覆尋找紀錄。反過來，先找出收到請求的不同伺服器即可：

```text
零請求伺服器數 = n - 區間內至少收到一次請求的不同伺服器數
```

例如區間內的伺服器編號為 `1,1,2,1,2`，有五筆請求，但只有兩台活躍伺服器。若 `n = 3`，答案就是 `3 - 2 = 1`。

最直覺的做法是每個查詢重新掃描紀錄並去重，得到暴力解法。但紀錄數與查詢數都可達十萬，最多需要約 `10^10` 次紀錄判斷。因此主要解法改為按時間處理查詢，重用相鄰區間的資訊。

## 方法一：排序與滑動視窗

對應方法：`CountServers(int n, int[][] logs, int x, int[] queries)`。

### 1. 出發點：沿用上一個查詢，不必全部重算

先看 `x = 5`、查詢時間依序為 `10、11、12` 的情況：

```text
q = 10：時間區間 [5,10]
q = 11：時間區間 [6,11]
q = 12：時間區間 [7,12]

時間          5   6   7   8   9  10  11  12
[5,10]        [-------------------]
[6,11]            [-------------------]
[7,12]                [-------------------]
```

相鄰區間有大量重疊。從 `[5,10]` 走到 `[6,11]` 時，原本時間 6 到 10 的紀錄都能沿用，只要排除時間 5 的舊紀錄，並納入時間 11 的新紀錄。這就是此處「滑動視窗」的想法：**保留統計狀態，只更新進出區間的紀錄。**

為了快速找到這些紀錄，先把 `logs` 按時間排序。若查詢時間也由小到大處理，因為 `x` 固定，左右端點都只會往右走；已經過期的紀錄，以後也不可能重新有效。如何處理原本未排序的查詢，會在最後一節說明。

> [!NOTE]
> 此方法會原地排序 `logs` 的外層陣列，但不改寫每筆紀錄的兩個數值，也不修改 `queries`。若要保留原始紀錄順序，請先複製。範例測試為每次呼叫提供外層與內層都獨立的副本。

### 2. `cnt` 計算請求筆數，`active` 計算伺服器台數

題目要算零請求的伺服器數，所以先維護「至少收到一次請求的伺服器數量」`active`，最後回傳 `n - active`。

但只有 `active` 還不夠。例如目前統計中的紀錄為 `[1,3]、[1,5]、[2,6]`：

```text
cnt[1] = 2：伺服器 1 有兩筆請求
cnt[2] = 1：伺服器 2 有一筆請求
cnt[3] = 0：伺服器 3 沒有請求
active = 2：有請求的伺服器共兩台，不是三台
```

當 `[1,3]` 過期時，伺服器 1 還有 `[1,5]`，因此 `cnt[1]` 從 2 變成 1，`active` 不變。等 `[1,5]` 也過期，`cnt[1]` 歸零，才能將 `active` 減一。

| 動作 | 該台請求次數變化 | `active` 變化 | 原因 |
|---|---|---|---|
| 加入第一筆 | `0 → 1` | 加一 | 新增一台活躍伺服器 |
| 加入另一筆 | `1 → 2` | 不變 | 仍是同一台伺服器 |
| 移除其中一筆 | `2 → 1` | 不變 | 這台還有其他請求 |
| 移除最後一筆 | `1 → 0` | 減一 | 這台不再活躍 |

只有集合，無法直接判斷移除一筆紀錄後，同台是否仍有其他有效請求。`cnt` 保存這項資訊，讓每次加入或移除只需更新一個計數位置。

`cnt` 配置成 `new int[n + 1]`，讓編號 `1..n` 能直接當索引；`cnt[0]` 不使用。下文的計數 `[a,b,c]` 都表示 `[cnt[1],cnt[2],cnt[3]]`，省略索引 0。

### 3. `left`、`right` 是陣列索引，不是時間

請區分兩種範圍：

| 範圍 | 意義 | 例子 |
|---|---|---|
| 時間區間 `[q-x,q]` | 本次查詢接受的請求時間，包含兩端 | `[5,10]` |
| 紀錄索引 `[left,right)` | 目前納入計數的陣列位置，包含 left、不包含 right | `[1,3)`，即索引 1、2 |

假設排序後有四筆紀錄，且目前 `left = 1`、`right = 3`：

```text
索引       0       1       2        3
紀錄     [1,3]   [1,5]   [2,6]   [3,12]
                  ^                ^
                left             right

目前納入計數：索引 1、2，也就是 [1,5]、[2,6]
right 指到的索引 3 尚未加入。
```

`logs[k][0]` 是伺服器編號，`logs[k][1]` 是請求時間，`k` 才是紀錄索引。

| 狀態 | 用途 |
|---|---|
| `left` | 指向第一筆尚未移除的紀錄 |
| `right` | 指向下一筆尚未加入的紀錄 |
| `cnt[id]` | 目前已加入且未移除的該台請求筆數 |
| `active` | 目前 `cnt[id] > 0` 的伺服器數量 |
| `ans[i]` | 原始第 i 個查詢的答案 |

初始 `left = right = 0`，表示尚無紀錄。當 `left == right`，目前統計區間為空；當 `right == logs.Length`，表示所有紀錄都已加入過，不能再用這個索引讀取陣列。

### 4. 兩個 while：先加入，再排除過期紀錄

對每個查詢 `q`，程式分三步進行。

**第一步：右指標加入時間不超過 q 的新紀錄。**

```csharp
while (right < logs.Length && logs[right][1] <= q)
```

`right < logs.Length` 防止讀取超出陣列範圍；`time <= q` 表示右端點也算在內。因為紀錄已排序，一旦下一筆時間大於 q，後面的紀錄也不符合，便能停止。

這一步只檢查右端點，所以也可能加入早於 `q-x` 的紀錄。它們會在下一步排除，這時還不能計算答案。

**第二步：左指標移除時間嚴格小於 q-x 的紀錄。**

```csharp
while (left < right && logs[left][1] < q - x)
```

`left < right` 表示還有已加入的紀錄可移除，避免處理尚未加入的紀錄。移除條件必須用 `<`，因為時間剛好等於 `q-x` 仍然有效。

這裡的「加入／移除」只更新 `cnt`、`active` 與指標，**不會新增或刪除 logs 的元素**。若兩個查詢相距很遠，某筆紀錄可能剛加入就被排除，仍不影響正確性。

**第三步：統計完成後，把答案寫回原始查詢位置。**

```csharp
ans[i] = n - active;
```

兩個 while 都結束後，`[left,right)` 中的紀錄才恰好對應時間區間 `[q-x,q]`，而 `active` 就是區間內不同活躍伺服器的數量。這項每次算答案前都成立的性質，就是演算法的不變量。

### 5. 官方範例一完整演示

```text
n = 3, x = 5, queries = [10,11]
原始 logs = [[1,3],[2,6],[1,5]]
排序 logs = [[1,3],[1,5],[2,6]]
紀錄索引       0     1     2
初始 left = right = active = 0
```

以下計數寫作 `[cnt[1],cnt[2],cnt[3]]`：

| 查詢 | 動作 | left | right | 計數 | active | 答案 |
|---|---|---:|---:|---|---:|---|
| `10 → [5,10]` | 加入 `[1,3]` | 0 | 1 | `[1,0,0]` | 1 | 尚未計算 |
| 同上 | 加入 `[1,5]`，同台重複請求 | 0 | 2 | `[2,0,0]` | 1 | 尚未計算 |
| 同上 | 加入 `[2,6]` | 0 | 3 | `[2,1,0]` | 2 | 尚未計算 |
| 同上 | 移除 `[1,3]`，時間小於 5 | 1 | 3 | `[1,1,0]` | 2 | `3-2=1` |
| `11 → [6,11]` | 無新紀錄可加入 | 1 | 3 | `[1,1,0]` | 2 | 尚未計算 |
| 同上 | 移除 `[1,5]`，伺服器 1 次數歸零 | 2 | 3 | `[0,1,0]` | 1 | `3-1=2` |

第一個查詢移除 `[1,3]` 時，伺服器 1 還有時間 5 的請求，因此 `active` 不能減少。第二個查詢移除它最後一筆有效請求後，才減少 `active`。

最後回傳 `[1,2]`。兩個指標整段過程都沒有向左退。

### 6. 延伸教學範例：下一個查詢同時加入與移除

以下是額外的教學推演，並非新增至 `Main` 的固定案例。在官方範例後面多放一筆時間 12 的請求，觀察右指標如何繼續前進：

```text
n = 3, x = 5
logs = [[1,3],[1,5],[2,6],[3,12]]
queries = [10,11,12]
預期答案 = [1,2,2]
```

初始 `left = right = active = 0`，計數為 `[0,0,0]`。下表逐筆列出狀態；「計數」仍省略 `cnt[0]`。

| q / 時間區間 | 動作 | left | right | 計數 | active | 答案 |
|---|---|---:|---:|---|---:|---|
| `10 / [5,10]` | 加入 `[1,3]` | 0 | 1 | `[1,0,0]` | 1 | 尚未計算 |
| 同上 | 加入 `[1,5]` | 0 | 2 | `[2,0,0]` | 1 | 尚未計算 |
| 同上 | 加入 `[2,6]` | 0 | 3 | `[2,1,0]` | 2 | 尚未計算 |
| 同上 | `[3,12]` 超過右端點，停止加入 | 0 | 3 | `[2,1,0]` | 2 | 尚未計算 |
| 同上 | 移除 `[1,3]`；下一筆時間 5 仍有效 | 1 | 3 | `[1,1,0]` | 2 | `3-2=1` |
| `11 / [6,11]` | `[3,12]` 尚未到時間，無新增 | 1 | 3 | `[1,1,0]` | 2 | 尚未計算 |
| 同上 | 移除 `[1,5]`；下一筆時間 6 仍有效 | 2 | 3 | `[0,1,0]` | 1 | `3-1=2` |
| `12 / [7,12]` | 加入 `[3,12]`，已到陣列末端 | 2 | 4 | `[0,1,1]` | 2 | 尚未計算 |
| 同上 | 移除 `[2,6]`；下一筆時間 12 仍有效 | 3 | 4 | `[0,0,1]` | 1 | `3-1=2` |

第一個查詢先加入時間 3，是因為第一個 while 只看 `time <= 10`；第二個 while 才用 `time < 5` 排除它。不要把中間暫時的 `cnt` 當成最後答案的統計。

到 q=11 時，直接沿用上一輪資料，只有一筆需要移除。到 q=12 時，先加入 `[3,12]`，再移除 `[2,6]`，最後只剩伺服器 3 活躍。

每個查詢完成後，陣列中被統計的部分如下：

```text
索引                 0       1       2        3
紀錄               [1,3]   [1,5]   [2,6]   [3,12]
q=10：left=1,right=3        |---- 統計 ----|            索引 1、2
q=11：left=2,right=3                |統計|              索引 2
q=12：left=3,right=4                         |統計|     索引 3
```

表格與圖中 `right` 都是「下一筆」的位置。最後 `right=4` 等於紀錄數量，沒有 `logs[4]` 這筆資料。

### 7. 將程式中的 ++、-- 簡寫拆開理解

**取出紀錄，再移動指標：**

```csharp
int id = logs[right++][0];
```

`right++` 使用原本的索引讀取紀錄，再將索引加一，等價於：

```csharp
int id = logs[right][0];
right++;
```

同理，`int id = logs[left++][0];` 表示先取出即將移除的伺服器編號，再把 `left` 往右移一格。

**加入紀錄時，使用增加前的次數判斷：**

```csharp
if (cnt[id]++ == 0)
{
    ++active;
}
```

後置 `++` 的比較使用舊值，但計數本身每次都會加一。可展開為以下等價步驟：

```csharp
int previousCount = cnt[id];
cnt[id]++;
if (previousCount == 0)
{
    active++;
}
```

例如舊值為 0，就新增一台活躍伺服器；舊值為 1，只增加請求筆數。

**移除紀錄時，使用減少後的次數判斷：**

```csharp
if (--cnt[id] == 0)
{
    --active;
}
```

前置 `--` 先減一，再判斷新值，等價於：

```csharp
cnt[id]--;
if (cnt[id] == 0)
{
    active--;
}
```

減少後仍大於 0，代表這台還有有效請求；只有歸零才能減少活躍台數。

### 8. 為什麼排序查詢索引？如何還原答案？

如果先處理 q=11 的 `[6,11]`，再處理 q=6 的 `[1,6]`，就需要找回已移除的較早紀錄。原本只向右移動的雙指標無法直接完成這種倒退，因此必須按查詢時間排序處理。

這稱為「離線查詢」：所有查詢事先已知，可以先調整處理順序，再還原答案位置。

```csharp
int[] ids = Enumerable.Range(0, queries.Length).ToArray();
Array.Sort(ids, (i, j) => queries[i].CompareTo(queries[j]));
```

第一行建立原始索引 `0,1,2,...`；第二行比較的是各索引對應的查詢時間，只改變 `ids`，不改變 `queries`。

回到官方範例一的 `n`、`logs`、`x`（沒有額外的 `[3,12]`），改用 `queries = [11,6,10,6]`。

```text
原始索引：  0  1   2  3
查詢時間： 11  6  10  6
```

索引按照查詢時間排序後可以是 `[1,3,2,0]`；相同時間的索引先後順序不影響答案。

| 處理的原索引 | q / 區間 | 新增紀錄 | 移除紀錄 | 最終計數 | active | 寫回答案 |
|---:|---|---|---|---|---:|---|
| 1 | `6 / [1,6]` | `[1,3],[1,5],[2,6]` | 無 | `[2,1,0]` | 2 | `ans[1]=1` |
| 3 | `6 / [1,6]` | 無 | 無 | `[2,1,0]` | 2 | `ans[3]=1` |
| 2 | `10 / [5,10]` | 無 | `[1,3]` | `[1,1,0]` | 2 | `ans[2]=1` |
| 0 | `11 / [6,11]` | 無 | `[1,5]` | `[0,1,0]` | 1 | `ans[0]=2` |

回傳 `[2,1,1,1]`，對應原始查詢順序，而非處理順序。

`foreach (int i in ids)` 中的 i 是原始查詢索引，因此 `q = queries[i]` 取得本輪時間，`ans[i] = n - active` 則直接把答案放回正確位置。若改用處理順序依次填入答案，就會得到排序後的順序，而非題目要求的順序。

相同查詢時間的區間完全相同，因此重複查詢不需要移動指標，也不要求排序保留相同元素的原先順序。

每筆紀錄最多由 right 加入一次、由 left 移除一次。即使程式有巢狀 while，所有查詢合計也只有 O(L) 次指標移動，並非每個查詢都掃描 L 筆；加上排序與陣列初始化後的完整成本，見下方「複雜度比較」。

## 方法二：暴力掃描與集合

對應方法：`CountServersBruteForce(int n, int[][] logs, int x, int[] queries)`。

### 設計與流程

每個查詢各自建立空的 `HashSet<int>`，從頭到尾掃描 `logs`。若 `q-x <= time && time <= q`，就將伺服器編號加入集合。最後以 `n - activeServers.Count` 得到答案。

集合會自動去重，所以同一台收到多次請求也只計一次。不同查詢使用不同集合，避免前一個區間的活躍伺服器殘留。直接按照輸入順序迭代查詢，答案自然保留原始順序，不需要排序。

此方法不修改 `logs` 或 `queries`，設計直覺，適合學習題意及作為小型測試的參考答案；大規模輸入應使用滑動視窗。

### 範例一完整演示

使用原始紀錄順序 `[[1,3],[2,6],[1,5]]`，不先排序。

| 查詢 / 區間 | 掃描紀錄 | 判斷 | 集合內容 | 不同活躍數 |
|---|---|---|---|---:|
| `10 / [5,10]` | `[1,3]` | 3 小於 5，跳過 | `{}` | 0 |
| 同上 | `[2,6]` | 6 在區間內，加入 2 | `{2}` | 1 |
| 同上 | `[1,5]` | 5 等於左端點，加入 1 | `{1,2}` | 2 |
| `11 / [6,11]` | `[1,3]` | 新集合；3 小於 6，跳過 | `{}` | 0 |
| 同上 | `[2,6]` | 6 等於左端點，加入 2 | `{2}` | 1 |
| 同上 | `[1,5]` | 5 小於 6，跳過 | `{2}` | 1 |

兩個查詢分別得到 `3-2=1`、`3-1=2`，回傳 `[1,2]`。表格中的集合只呈現成員，集合本身不保證列舉順序。

## 複雜度比較

令 `L = logs.Length`、`Q = queries.Length`。

| 面向 | 排序＋滑動視窗 | 暴力掃描＋集合 |
|---|---|---|
| 時間 | `O(L log L + Q log Q + n)` | 平均 `O(Q × L)` |
| 工作資料，不含答案與排序堆疊 | `O(n + Q)`：計數與查詢索引 | `O(min(n,L))`：單次查詢集合 |
| 排序呼叫堆疊 | `O(log L + log Q)` 的保守上界 | 無排序 |
| 回傳陣列 | `O(Q)` | `O(Q)` |
| 輸入副作用 | 原地排序 `logs` | 不修改輸入 |
| 使用情境 | 題目完整資料規模 | 小型驗證、理解題意 |

滑動視窗的兩個指標合計只做 `O(L)` 次移動；每個查詢額外 `O(1)`，因此掃描部分為 `O(L+Q)`。`cnt` 的配置與零初始化需要 `O(n)`，納入總時間。排序使用 .NET `Array.Sort`，兩次排序依序執行，上表堆疊上界已足夠涵蓋所需空間。

暴力解法平均時間以 `HashSet.Add` 平均 `O(1)` 為前提。每個查詢都掃描全部 `L` 筆，因此即使視窗很小也不能省掉掃描成本。

測試程式另外配置輸入副本，這些配置不屬於演算法方法本身的空間複雜度。
