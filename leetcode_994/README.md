# LeetCode 994：腐爛的橘子

[![.NET 10](https://img.shields.io/badge/.NET-10.0-512BD4?logo=dotnet)](https://dotnet.microsoft.com/)

專案提供兩種多源廣度優先搜尋（Breadth-First Search, BFS）解法，並由 `Main`

- 題目：[Rotting Oranges](https://leetcode.com/problems/rotting-oranges/)
- 中文題目：[腐爛的橘子](https://leetcode.cn/problems/rotting-oranges/)

## 題目說明

給定一個 `m x n` 的網格 `grid`，每個儲存格只會包含以下三種值之一：

- `0`：空格。
- `1`：新鮮橘子。
- `2`：腐爛橘子。

每經過一分鐘，腐爛橘子會使上、下、左、右四個方向中相鄰的新鮮橘子腐爛。

請回傳直到網格中沒有新鮮橘子為止所需的最少分鐘數。如果存在永遠無法被任何
腐爛橘子抵達的新鮮橘子，回傳 `-1`。

### 官方範例一

```text
輸入：grid = [[2,1,1],[1,1,0],[0,1,1]]
輸出：4
```

腐爛會逐分鐘由左上角向外傳播，最遠的右下角橘子會在第 4 分鐘腐爛。

### 官方範例二

```text
輸入：grid = [[2,1,1],[0,1,1],[1,0,1]]
輸出：-1
```

左下角的新鮮橘子被空格隔開，無法透過四方向相鄰關係連接到任何腐爛橘子。

### 官方範例三

```text
輸入：grid = [[0,2]]
輸出：0
```

起始狀態已經沒有新鮮橘子，因此不需要等待。

### 限制條件

- `m == grid.Length`
- `n == grid[i].Length`
- `1 <= m, n <= 10`
- `grid[i][j]` 只會是 `0`、`1` 或 `2`

## 解題概念與出發點

### 為什麼這是一個最短路徑問題

可以把每一個非空儲存格想成圖上的節點。若兩個橘子在上下左右相鄰，它們之間就
有一條長度為一分鐘的邊。某顆新鮮橘子何時腐爛，等同於：

> 從任一初始腐爛橘子出發，到達該新鮮橘子的最短距離是多少？

BFS 會依照距離由近到遠拜訪節點，因此第一次抵達某顆新鮮橘子時，使用的分鐘數
一定最少。

### 為什麼必須使用多源 BFS

題目中的所有腐爛橘子都會在同一分鐘同步擴散。如果分別從每顆腐爛橘子執行
BFS，不只會重複走訪網格，也較難正確表達「同步」。

多源 BFS 的作法是：

1. 先掃描整個網格。
2. 把所有初始腐爛橘子一起放入佇列。
3. 將它們全部視為第 0 分鐘的起點。
4. 再以一般 BFS 向外擴散。

這相當於建立一個虛擬起點，並讓它以零成本連接所有初始腐爛橘子。如此只需要
一次 BFS，就能求出每顆新鮮橘子的最早腐爛時間。

### 共同的重要判斷

兩種解法都遵守以下規則：

- 只走上、左、下、右，不走對角線。
- 只有值為 `1` 的新鮮橘子可以被加入下一輪傳播。
- 新鮮橘子一入列就立刻改成 `2`，避免被不同來源重複加入佇列。
- 起始狀態沒有新鮮橘子時回傳 `0`。
- BFS 結束後仍有新鮮橘子時回傳 `-1`。

## 解法一：座標壓縮與深度字典

公開方法：

```csharp
public static int OrangesRotting(int[][] grid)
```

### 設計想法

第一種解法為每個腐爛橘子保存明確的 BFS 深度，也就是該橘子腐爛的分鐘數。
佇列只儲存一個整數，因此會先將二維座標壓縮成一維編碼。

假設網格共有 `columns` 欄，座標 `(row, column)` 的編碼為：

```text
code = row * columns + column
```

還原方式為：

```text
row = code / columns
column = code % columns
```

因為每一列恰好有 `columns` 個位置，所以不同座標不會得到相同編碼。

### 使用的資料結構

- `Queue<int>`：依 BFS 順序保存壓縮後的座標。
- `Dictionary<int, int>`：以座標編碼為 key，保存該位置的腐爛分鐘數。
- `RowOffsets`、`ColumnOffsets`：表示上、左、下、右四個方向。

### 執行步驟

1. 掃描網格，將所有值為 `2` 的位置編碼後加入佇列。
2. 將每個初始腐爛橘子的深度設為 `0`。
3. 從佇列取出一個位置，還原成 `(row, column)`。
4. 檢查四個相鄰位置。
5. 遇到新鮮橘子時，立刻將它改成 `2`，並把深度設為目前深度加一。
6. 記錄目前看到的最大深度。
7. BFS 結束後掃描網格；若仍存在 `1`，回傳 `-1`，否則回傳最大深度。

### 為什麼入列時就要標記

假設同一顆新鮮橘子同時鄰接兩顆腐爛橘子。如果等到出列才標記，兩個來源可能都
將它加入佇列，造成重複處理。入列時立即改成 `2`，就能保證每個位置最多入列
一次，也使時間複雜度維持在線性範圍。

### 正確性說明

BFS 會先處理深度較小的位置，再處理深度較大的位置。所有初始腐爛橘子的深度
都是 `0`，而每次傳播都讓新橘子的深度增加 `1`。

因此，某顆新鮮橘子第一次被加入佇列時，其深度就是從任一初始腐爛橘子抵達它的
最短四方向距離，也就是它最早能腐爛的分鐘數。全部可達橘子中最大的深度，就是
所有橘子腐爛所需的最少時間。

若 BFS 結束後仍有值為 `1` 的位置，代表該位置不在任何腐爛來源可達的連通區域，
所以答案必須是 `-1`。

### 複雜度

令網格大小為 `m x n`：

| 項目 | 複雜度 | 說明 |
| --- | --- | --- |
| 時間 | `O(mn)` | 初始化、BFS 與最後檢查各自最多掃描整個網格一次 |
| 額外空間 | `O(mn)` | 最壞情況下佇列與深度字典都保存所有橘子 |

### 範例演示流程

使用官方範例一：

```text
grid = [[2,1,1],[1,1,0],[0,1,1]]
columns = 3
```

初始腐爛橘子位於 `(0, 0)`：

```text
code = 0 * 3 + 0 = 0
depth[0] = 0
queue = [0]
```

各分鐘的狀態如下，`R` 表示本分鐘以前已腐爛的位置：

| 分鐘 | 新腐爛座標 | 對應編碼 | 最大深度 |
| ---: | --- | --- | ---: |
| 0 | `(0, 0)` | `0` | 0 |
| 1 | `(0, 1)`、`(1, 0)` | `1`、`3` | 1 |
| 2 | `(0, 2)`、`(1, 1)` | `2`、`4` | 2 |
| 3 | `(2, 1)` | `7` | 3 |
| 4 | `(2, 2)` | `8` | 4 |

最後沒有新鮮橘子，最大深度為 `4`，因此回傳 `4`。

## 解法二：逐層佇列與新鮮橘子計數

公開方法：

```csharp
public static int OrangesRotting2(int[][] grid)
```

### 設計想法

第二種解法不為每個位置保存深度，而是利用「目前佇列中有多少個元素」劃分 BFS
層級。進入每一分鐘前先記下 `queue.Count`，只處理這些已經腐爛的橘子。

處理過程中才加入佇列的新橘子屬於下一分鐘，因此不能在同一層繼續傳播。當本層
全部處理完成後，分鐘數才增加一。

同時維護 `freshCount`：

- 初次掃描時，遇到 `1` 就加一。
- 新鮮橘子腐爛時減一。
- BFS 結束後，`freshCount == 0` 表示成功；否則回傳 `-1`。

### 使用的資料結構

- `Queue<(int Row, int Column)>`：直接保存列、欄座標，不需要編碼與解碼。
- `freshCount`：保存尚未腐爛的新鮮橘子數量。
- `currentLevelCount`：固定本分鐘可以向外傳播的腐爛橘子數量。

### 執行步驟

1. 掃描網格，將所有腐爛橘子加入佇列，並計算新鮮橘子數量。
2. 當佇列不為空且仍有新鮮橘子時，記錄本層的 `queue.Count`。
3. 只取出本層既有的橘子，檢查它們的四個相鄰位置。
4. 新鮮橘子腐爛時立刻標記、將 `freshCount` 減一，並加入佇列尾端。
5. 本層處理完成後，分鐘數加一。
6. 最後依 `freshCount` 回傳分鐘數或 `-1`。

### 為什麼外層條件要檢查 freshCount

若起始網格沒有新鮮橘子，例如 `[[0, 2]]`，答案應為 `0`。使用
`freshCount > 0` 作為迴圈條件，可以避免僅僅處理既有腐爛橘子就錯誤增加分鐘。

當最後一顆新鮮橘子腐爛後，也不必再處理只含腐爛橘子的下一層，因為答案已經
確定。

### 正確性說明

在每次外層迴圈開始時，佇列前 `currentLevelCount` 個位置恰好代表目前分鐘已經
腐爛、能在下一分鐘傳播的所有橘子。內層迴圈只處理這些位置，新加入的位置留給
下一層，因此一次外層迴圈精確對應一分鐘。

由於所有初始來源同時入列，而且 BFS 逐層向外擴散，每顆新鮮橘子第一次入列的
層級就是最早腐爛時間。當 `freshCount` 變為零時，累積的層數就是全部腐爛所需
的最少分鐘數。

若佇列先變空但 `freshCount` 仍大於零，就代表剩餘橘子無法由任何來源抵達，
因此回傳 `-1`。

### 複雜度

令網格大小為 `m x n`：

| 項目 | 複雜度 | 說明 |
| --- | --- | --- |
| 時間 | `O(mn)` | 每個位置最多掃描一次並入列一次 |
| 額外空間 | `O(mn)` | 最壞情況下佇列同時保存大量橘子 |

### 範例演示流程

同樣使用官方範例一。初次掃描後：

```text
queue = [(0, 0)]
freshCount = 6
minutes = 0
```

| 外層迴圈 | 本層開始 queue.Count | 本分鐘新腐爛數 | freshCount | minutes |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 2 | 4 | 1 |
| 2 | 2 | 2 | 2 | 2 |
| 3 | 2 | 1 | 1 | 3 |
| 4 | 1 | 1 | 0 | 4 |

第 4 層完成後 `freshCount == 0`，停止 BFS 並回傳 `4`。

## 兩種解法比較

| 比較項目 | 解法一：座標壓縮＋深度字典 | 解法二：逐層佇列＋新鮮計數 |
| --- | --- | --- |
| 座標保存 | 壓縮成單一 `int` | 使用 `(Row, Column)` tuple |
| 時間追蹤 | 每個位置保存明確深度 | 每處理一個完整 BFS 層加一分鐘 |
| 完成判斷 | BFS 後再次掃描是否仍有 `1` | 直接檢查 `freshCount` |
| 時間複雜度 | `O(mn)` | `O(mn)` |
| 額外空間 | `O(mn)` | `O(mn)` |
| 教學重點 | 座標映射、最短距離與深度 | BFS 分層、同步傳播與計數 |

兩者的漸近複雜度相同。解法一能直接查到每顆橘子的腐爛深度；解法二不需要深度
字典，並能透過 `freshCount` 提早知道是否已經全部腐爛。

## 輸入副作用

兩種公開方法都會直接修改傳入的 `grid`，把已腐爛的新鮮橘子從 `1` 改成 `2`。
這符合常見的 LeetCode 原地標記寫法，可避免另外建立 `visited` 網格。

主程式在呼叫每種解法前都使用 `CloneGrid` 深層複製測試資料，原因有二：

1. 第一種解法執行後不會影響第二種解法的輸入。
2. Console 仍能顯示原始網格，而不是已經全部腐爛後的狀態。
