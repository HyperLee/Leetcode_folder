# LeetCode 3789｜滿足採購需求的最低成本

使用 C# 貪心法，在常數時間內算出滿足兩類需求的最低成本。專案以 .NET 10 主控台執行測資。

## 題目說明

給定三種物品的單價，以及兩類需求的最低數量。每種物品可購買任意非負整數件，目標是以最低總成本讓兩類需求都達標。

| 物品 | 單價 | 第 1 類貢獻 | 第 2 類貢獻 |
| --- | ---: | ---: | ---: |
| 第 1 類 | `cost1` | 1 | 0 |
| 第 2 類 | `cost2` | 0 | 1 |
| 第 3 類 | `costBoth` | 1 | 1 |

`need1` 與 `need2` 是達標門檻。若其中一類已達標，仍可購買第 3 類物品來滿足另一類，即使會讓已達標的一類超額。

### 限制條件

- `1 <= cost1, cost2, costBoth <= 10^6`
- `0 <= need1, need2 <= 10^9`
- 輸入為五個整數，回傳最低總成本。C# 使用 `long` 儲存結果。

### 官方範例

| 輸入 `(cost1, cost2, costBoth, need1, need2)` | 最低成本 | 購買方式 |
| --- | ---: | --- |
| `(3, 2, 1, 3, 2)` | 3 | 買 3 件第 3 類，兩類各得到 3 單位。 |
| `(5, 4, 15, 2, 3)` | 22 | 買 2 件第 1 類與 3 件第 2 類。 |
| `(5, 4, 15, 0, 0)` | 0 | 買 0 件。 |

[LeetCode 官方題目](https://leetcode.com/problems/minimum-cost-to-acquire-required-items/description/)

## 貪心解法 `MinimumCost`

### 先記住：現在缺什麼，就比較能補足它的買法

以下用 **A** 表示第 1 類需求，**B** 表示第 2 類需求；A 單品、B 單品分別是第 1、2 類物品，**AB 組合包**是第 3 類物品。

一件 AB 組合包固定提供 A、B 各 1 單位，不能改成提供 2 個 A 或 2 個 B。

```text
A、B 都需要：
    組合包 vs. 兩種單品各一件
    比較 costBoth 與 cost1 + cost2

只剩 A：
    組合包 vs. A 單品
    比較 costBoth 與 cost1

只剩 B：
    組合包 vs. B 單品
    比較 costBoth 與 cost2
```

**比較哪些價格，取決於當下還需要補足哪些需求。** 兩類都缺時，組合包可以同時取代兩件單品；只剩一類缺時，組合包只能取代該類的一件單品，另一類的貢獻會成為超額供應。

### 依照程式逐步理解

#### 步驟 1：判斷是否全部買單品即可

```csharp
if (cost1 + cost2 <= costBoth)
{
    totalCost = 1L * cost1 * need1 + 1L * cost2 * need2;
}
```

當 A、B 各缺 1 單位時，買兩種單品各一件與買一件組合包，得到的貢獻相同。若 `cost1 + cost2 <= costBoth`，分開買較便宜或同價。

而且兩種單價都為正，所以此時 `cost1 < costBoth`、`cost2 < costBoth`。即使只缺 A 或只缺 B，組合包也沒有價格優勢。因此直接用各類單價乘上需求量即可。

例如 `(5, 4, 15, 2, 3)`：兩件單品合計 9 元，比組合包的 15 元便宜；全部買單品的成本為 `2 * 5 + 3 * 4 = 22`。

#### 步驟 2：組合包較便宜，先補共同需求

進入 `else` 表示 `costBoth < cost1 + cost2`，因此每一對「A、B 各缺 1 單位」的共同需求，都適合用組合包處理。

```csharp
int pairedCount = Math.Min(need1, need2);
totalCost = 1L * pairedCount * costBoth;
```

若 `need1 = 3`、`need2 = 2`，需求可以這樣配對：

```text
                 第 1 對   第 2 對   未配對
A 需求：           [A]       [A]       [A]
B 需求：           [B]       [B]
                   |         |
                 AB 一件   AB 一件

共同需求 = min(3, 2) = 2 對
剩餘需求 = A 一個
```

`pairedCount` 是**兩類都需要的配對數，不是組合包的購買上限**。先買 2 件組合包後，是否要為剩餘的 A 再買組合包，要在下一階段重新比較價格。

#### 步驟 3：扣掉已補足的需求

```csharp
need1 -= pairedCount;
need2 -= pairedCount;
```

上述例子的剩餘需求會從 `(3, 2)` 變成 `(1, 0)`。因為兩邊都扣掉原本的最小值，**至少一邊一定變成 0**；若原本需求相等，則兩邊都變成 0。

因此後面使用 `if / else if`，只需要處理其中一類的剩餘需求。這裡的 `need1`、`need2` 已改為表示尚未補足的數量。

#### 步驟 4：只剩一類需求，重新比較價格

```csharp
if (need1 > 0)
{
    totalCost += 1L * need1 * Math.Min(cost1, costBoth);
}
else if (need2 > 0)
{
    totalCost += 1L * need2 * Math.Min(cost2, costBoth);
}
```

假設只剩 A，每補 1 單位有兩種買法：買 A 單品，花費 `cost1`；或買組合包，花費 `costBoth`，同時多得到一個已不需要的 B。

題目只要求「至少」滿足需求，允許 B 超額，所以每個剩餘 A 的成本是 `Math.Min(cost1, costBoth)`。只剩 B 時同理，使用 `Math.Min(cost2, costBoth)`。若兩邊都為 0，這兩個分支都不執行。

**組合包比兩件單品合計便宜，不代表它比其中一件單品也便宜。** 例如 `cost1 = 6`、`cost2 = 3`、`costBoth = 5`：共同需求選組合包，因為 `5 < 6 + 3`；但只剩 B 時選 B 單品，因為 `3 < 5`。

### 為什麼能得到最低成本

先用替換買法來理解：當組合包比兩件單品合計便宜時，只要某個買法中還有 A、B 單品各一件，就可以把這兩件換成一件組合包。得到的 A、B 數量相同，成本卻降低。因此共同需求應持續用組合包替換，直到其中一類達標，也就是先處理 `min(need1, need2)` 對。

之後只剩一類需求，單品與組合包都能補足它，每個單位都選較便宜的即可。若兩件單品合計比組合包便宜或同價，則反過來把組合包換成兩件單品不會增加成本，全部買單品就有最低成本。

也可以用公式確認。以下 `need1`、`need2` 指原始需求，`pairedCount = min(need1, need2)`。假設買了 `x` 件第 3 類物品。固定 `x` 後，每類只需要用單類物品買到剛好補足缺口，因為再多買會增加成本。此時的最低成本為

```text
cost(x) = x * costBoth
        + max(need1 - x, 0) * cost1
        + max(need2 - x, 0) * cost2
```

- 當 `x < pairedCount`，多買 1 件第 3 類會同時少買兩種單類物品各 1 件，成本變化固定為 `costBoth - (cost1 + cost2)`。因此共同需求的每一對都可採用較便宜的方式。
- 當 `pairedCount <= x < max(need1, need2)`，再買 1 件第 3 類只會少買仍有缺口的單類物品 1 件，成本變化為 `costBoth - 該類單價`。此區間內比較的是這兩種物品的單價。
- 當 `x >= max(need1, need2)`，兩類都已達標，再買只會增加成本。

兩個區間的成本變化都固定。若第 3 類連一對單類物品都換得更貴，進入單邊區間後也不可能省錢。若替代一對單類物品可以省錢，就先買到配對上限，再由單邊價格決定要不要繼續買第 3 類。

### ASCII 流程圖

`n1`、`n2` 是當前需求，`c1`、`c2`、`cb` 是三種物品的單價。

```text
Start
  |
  v
c1 + c2 <= cb?
  +-- yes --> Return n1*c1 + n2*c2
  |
  +-- no ---> p = min(n1, n2)
              total = p*cb
              n1 = n1 - p, n2 = n2 - p
                |
                v
              n1 > 0?
                +-- yes --> Return total + n1*min(c1, cb)
                |
                +-- no ---> n2 > 0?
                             +-- yes --> Return total + n2*min(c2, cb)
                             |
                             +-- no ---> Return total
```

### 範例演示

**官方範例 1，共同購買後仍用第 3 類補足。** 輸入 `(3, 2, 1, 3, 2)`。

| 當下需求 | 比較價格 | 選擇 | 剩餘需求 `(A, B)` | 累計成本 |
| --- | --- | --- | --- | ---: |
| A、B 都需要 | 組合包 1 vs. 兩件單品合計 `3 + 2 = 5` | 買 2 件組合包 | `(1, 0)` | `2 * 1 = 2` |
| 只剩 A | 組合包 1 vs. A 單品 3 | 再買 1 件組合包 | `(0, 0)` | `2 + 1 * 1 = 3` |

最後總共買了 3 件組合包，**實際取得 A、B 各 3 個，B 超額 1 個**。表格與下圖的剩餘需求最低記為 0，超額不表示負的需求。

```text
Remaining (3, 2) | cost = 0
  -> buy 2 x type 3 -> remaining (1, 0) | cost = 0 + 2*1 = 2
  -> buy 1 x type 3 -> remaining (0, 0) | cost = 2 + 1*1 = 3
  -> return 3        (received 3 units of each type)
```

**官方範例 2，分開購買。** 輸入 `(5, 4, 15, 2, 3)`。組合包 15 元，兩件單品合計 `5 + 4 = 9` 元；而單獨補 A 的 5 元、補 B 的 4 元也都低於 15 元，因此全部買單品。程式直接計算 `2 * 5 + 3 * 4 = 22`，下表與流程把算式拆成兩筆採購。

| 採購步驟 | 選擇依據 | 剩餘需求 `(A, B)` | 累計成本 |
| --- | --- | --- | ---: |
| 買 2 件 A 單品 | A 單品 5 < 組合包 15 | `(0, 3)` | `2 * 5 = 10` |
| 買 3 件 B 單品 | B 單品 4 < 組合包 15 | `(0, 0)` | `10 + 3 * 4 = 22` |

```text
Remaining (2, 3) | cost = 0
  -> buy 2 x type 1 -> remaining (0, 3) | cost = 0 + 2*5 = 10
  -> buy 3 x type 2 -> remaining (0, 0) | cost = 10 + 3*4 = 22
  -> return 22
```

**第 2 類剩餘需求以單類物品補足。** 輸入 `(6, 3, 5, 1, 4)`。

| 當下需求 | 比較價格 | 選擇 | 剩餘需求 `(A, B)` | 累計成本 |
| --- | --- | --- | --- | ---: |
| A、B 都需要 | 組合包 5 vs. 兩件單品合計 `6 + 3 = 9` | 買 1 件組合包 | `(0, 3)` | `1 * 5 = 5` |
| 只剩 B | 組合包 5 vs. B 單品 3 | 買 3 件 B 單品 | `(0, 0)` | `5 + 3 * 3 = 14` |

第一階段比較 `5` 與 `9`，第二階段比較 `5` 與 `3`。需求不同，價格比較的對象也跟著改變，所以共同需求買組合包，剩餘需求改買 B 單品。

```text
Remaining (1, 4) | cost = 0
  -> buy 1 x type 3 -> remaining (0, 3) | cost = 0 + 1*5 = 5
  -> buy 3 x type 2 -> remaining (0, 0) | cost = 5 + 3*3 = 14
  -> return 14
```

### 複雜度與數值範圍

- 時間複雜度為 `O(1)`，因為只做固定次數的比較與算術運算。
- 額外空間複雜度為 `O(1)`，因為只保存固定數量的變數。
- 單價乘上需求量可達 `10^6 * 10^9 = 10^15`，超過 `int` 的上限。程式把 `1L` 放在乘法最前面，讓第一步就用 `long` 計算。若乘完才轉型，先前的 `int` 乘法可能已經溢位。
