# LeetCode 453：最小操作次數使陣列元素相等

![C#](https://img.shields.io/badge/C%23-68217A?logo=csharp&logoColor=white)
![.NET 10](https://img.shields.io/badge/.NET-10.0-512BD4?logo=dotnet&logoColor=white)

使用 C# 解題，示範如何把「每次增加 `n - 1` 個元素」轉換成最小值差額加總，並比較 LINQ 最小值搜尋、單次走訪公式計算與自行走訪找最小值這三種實作方式。

- [LeetCode 題目](https://leetcode.com/problems/minimum-moves-to-equal-array-elements/description/)
- [中文題目](https://leetcode.cn/problems/minimum-moves-to-equal-array-elements/description/)

## 題目說明

給定整數陣列 `nums`，每次操作可以將其中 `n - 1` 個元素各增加 `1`。請計算讓所有元素相等所需的最少操作次數。

例如 `nums = [1, 2, 3]` 的答案是 `3`。

## 限制條件

- `1 <= nums.length <= 10^5`
- `-10^9 <= nums[i] <= 10^9`
- 題目保證答案可用 32 位元有號整數表示。

## 解題概念與出發點

### 為什麼可以把增加轉換成減少？

直接模擬每次增加 `n - 1` 個元素，會讓陣列中的數字持續變大，也不容易看出最少操作次數。可以把一次操作拆成兩個動作：

1. 先替全部 `n` 個元素各加 `1`。
2. 再把唯一未被選中的元素減 `1`，抵消它剛才增加的部分。

所有元素共同增加 `1` 只會讓整個陣列平移，不會改變元素間的差距，也不影響「是否全部相等」。忽略這個共同增量後，一次原操作就等價於選一個元素減 `1`；兩種視角的操作次數相同。

以 `[1, 2, 3]` 為例，原題允許的操作序列是：

```text
[1, 2, 3] → [2, 3, 3] → [3, 4, 3] → [4, 4, 4]
```

每一步忽略全部元素共同增加的部分後，相當於：

```text
[1, 2, 3] → [1, 2, 2] → [1, 2, 1] → [1, 1, 1]
```

兩個序列都是三次操作。第二個視角讓我們直接看出：`3` 需要減少兩次，`2` 需要減少一次，`1` 不必減少。

### 為什麼目標是原陣列的最小值？

在等價視角中，元素只能減少。假設最後要全部變成 `target`，就必須滿足：

```text
target <= min(nums)
moves = Σ(nums[i] - target)
```

目標越低，每個元素需要減少的次數越多。例如選擇 `min(nums) - 1`，相較於選擇 `min(nums)`，全部 `n` 個元素都要再減少一次，總共多做 `n` 次。因此，選擇可達成的最高目標 `min(nums)`，就能得到最少操作次數：

```text
moves = Σ(nums[i] - min(nums))
```

這裡的最小值是「等價減少視角」的目標。原題實際操作會增加元素，例如上述範例最後得到 `[4, 4, 4]`，而不是 `[1, 1, 1]`；兩者之間相差三次操作所帶來的共同增量。

以下三種解法都實作這個公式，差別在於如何取得並組合所需資訊。三個方法都位於 `leetcode_453/Program.cs`。

## 解法一：最小值差額加總

對應方法：`MinMoves(int[] nums)`。先取得固定的最小值，再逐一計算每個元素與它的差額。

### 變數與執行步驟

| 變數 | 意義 |
| --- | --- |
| `minNum` | 完整陣列的最小值，由 `nums.Min()` 取得 |
| `num` | 第二次走訪時，目前處理的元素 |
| `res` | 已處理元素降到 `minNum` 所需的總次數，初始為 `0` |

1. `nums.Min()` 掃描陣列，取得最小值 `minNum`。
2. 再用 `foreach` 走訪每個元素。
3. 每次執行 `res += num - minNum`，把目前元素所需的減少次數加入答案。
4. 所有元素處理完後，回傳 `res`。整個過程不修改輸入陣列。

```csharp
int minNum = nums.Min();
int res = 0;

foreach (var num in nums)
{
    res += num - minNum;
}

return res;
```

### 範例演示：`[1, 2, 3]`

第一次走訪得到 `minNum = 1`。第二次走訪的變化如下：

| 步驟 | 元素 `num` | 固定最小值 `minNum` | 本次差額 `num - minNum` | 累加前 `res` | 累加後 `res` |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 1 | 0 | 0 | 0 |
| 2 | 2 | 1 | 1 | 0 | 1 |
| 3 | 3 | 1 | 2 | 1 | 3 |

三個元素分別需要減少 `0`、`1`、`2` 次，所以答案是 `0 + 1 + 2 = 3`。每一輪結束後，`res` 都等於已處理元素的差額總和；走訪結束時，它就涵蓋全部元素。

若輸入是 `[5, 6, 1]`，第一次走訪仍會先找到 `1`，因此第二次走訪從第一個元素開始就使用正確的最小值，得到 `(5 - 1) + (6 - 1) + (1 - 1) = 9`。

### 為什麼 `res` 使用 `int` 是安全的？

因為 `minNum` 是完整陣列的最小值，每個差額都大於等於 `0`。`res` 只會逐漸增加到最終答案，不會在中途超過最終答案；題目又保證答案能以 `int` 表示，因此累加過程是安全的。

此外，單一差額最大為 `1_000_000_000 - (-1_000_000_000) = 2_000_000_000`，也沒有超過 `int.MaxValue`。

### 複雜度

- 時間：`O(n)`，找最小值與累加各走訪一次，`O(n) + O(n)` 仍是 `O(n)`。
- 額外空間：`O(1)`，只使用固定數量的變數。

## 解法二：單次走訪計算總和與最小值

對應方法：`MinMoves2(int[] nums)`。把差額總和展開後，就可以在同一次走訪中收集總和與最小值，最後再計算答案。

### 公式推導

令 `n = nums.Length`，把每個元素的差額分開寫：

```text
moves = (nums[0] - minNum) + ... + (nums[n - 1] - minNum)
      = (nums[0] + ... + nums[n - 1]) - n × minNum
      = sum - n × minNum
```

`minNum` 總共被減了 `n` 次，所以能合併成 `n × minNum`。這個公式與解法一完全相同，只是改變加減運算的組合方式。

### 變數與執行步驟

| 變數 | 型別 | 意義與初始值 |
| --- | --- | --- |
| `minNum` | `int` | 目前找到的最小值，初始為 `nums[0]` |
| `sum` | `long` | 已處理元素的總和，初始為 `0` |
| `num` | `int` | 目前處理的元素 |
| `nums.Length` | `int` | 陣列長度，也就是公式中的 `n` |

1. 題目保證陣列非空，因此可以用 `nums[0]` 初始化 `minNum`。不能固定初始化為 `0`，否則全正數陣列可能得到不存在的最小值。
2. 用 `foreach` 走訪整個陣列，包含第一個元素。`sum` 從 `0` 開始，因此每個元素都恰好累加一次。
3. 每輪先執行 `sum += num`，再比較 `num` 與 `minNum`；若目前元素更小，就更新最小值。
4. 走訪結束後，使用完整陣列的總和與最小值，計算 `sum - n × minNum`。

```csharp
int minNum = nums[0];
long sum = 0;

foreach (int num in nums)
{
    sum += num;

    if (num < minNum)
    {
        minNum = num;
    }
}

return (int)(sum - ((long)minNum * nums.Length));
```

### 範例演示一：`[1, 2, 3]`

初始化：`sum = 0`、`minNum = 1`、`n = 3`。

| 步驟 | 元素 `num` | 累加前 `sum` | 累加後 `sum` | 比較前 `minNum` | `num < minNum` | 比較後 `minNum` |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| 1 | 1 | 0 | 1 | 1 | 否 | 1 |
| 2 | 2 | 1 | 3 | 1 | 否 | 1 |
| 3 | 3 | 3 | 6 | 1 | 否 | 1 |

走訪結束後，`sum = 6`、`minNum = 1`，所以答案是 `6 - 3 × 1 = 3`，與解法一相同。

### 範例演示二：`[5, 6, 1]`，最小值最後才出現

初始化：`sum = 0`、`minNum = 5`、`n = 3`。

| 步驟 | 元素 `num` | 累加前 `sum` | 累加後 `sum` | 比較前 `minNum` | `num < minNum` | 比較後 `minNum` |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| 1 | 5 | 0 | 5 | 5 | 否 | 5 |
| 2 | 6 | 5 | 11 | 5 | 否 | 5 |
| 3 | 1 | 11 | 12 | 5 | 是 | 1 |

前兩輪的最小值暫時是 `5`，第三輪才更新為 `1`。總和只累加原始元素，因此最小值更新時，不需要重算先前的 `sum`；最後直接得到 `12 - 3 × 1 = 9`。

若過早把當時的最小值當成最終最小值，直接累加 `num - minNum`，就可能少算。例如前兩個元素使用 `5` 作為基準，只算出 `0 + 1`；後來發現最小值是 `1` 時，前兩個元素的差額其實應該是 `4 + 5`。解法二透過最後統一減去 `n × minNum`，讓全部元素都使用同一個最終基準。

### 為什麼是先 `sum`，再比對 `minNum`？

先加總再比較，是目前程式採用的閱讀順序，並非正確性的必要條件。兩個動作彼此獨立：

- `sum += num` 只依賴舊的 `sum` 與目前元素 `num`，不使用 `minNum`。
- 最小值比較只依賴舊的 `minNum` 與目前元素 `num`，不使用 `sum`。

因此，交換成下面的順序也會得到相同結果：

```csharp
if (num < minNum)
{
    minNum = num;
}

sum += num;
```

以 `[5, 6, 1]` 的最後一輪為例，進入迴圈時 `sum = 11`、`minNum = 5`、`num = 1`。先加總會先得到 `sum = 12`，再更新 `minNum = 1`；先比較則先得到 `minNum = 1`，再把 `sum` 加到 `12`。兩者在這一輪結束時的狀態相同。

真正需要遵守的是：每一個元素都必須加入 `sum`，所以 `sum += num` 不能放進「找到更小值才執行」的 `if` 裡；最終答案也必須等整個陣列走訪完，再使用完整陣列的最小值計算。

### 為什麼 `sum` 與乘積需要 `long`？

題目保證的是最終答案能放入 `int`，並未保證元素總和與 `n × minNum` 能放入 `int`。例如十萬個 `1_000_000_000`：

```text
sum        = 100_000 × 1_000_000_000 = 100_000_000_000_000
n × minNum = 100_000 × 1_000_000_000 = 100_000_000_000_000
moves      = 0
```

答案雖然是 `0`，中間的兩個數卻都是 `10^14`，超過 `int.MaxValue = 2_147_483_647`。全為 `-1_000_000_000` 時，總和與乘積則會是 `-10^14`。題目範圍內的總和與乘積都能安全地用 `long` 表示。

因此使用 `long sum`，並在乘法之前將 `minNum` 轉為 `long`：

```csharp
sum - ((long)minNum * nums.Length)
```

若寫成 `(long)(minNum * nums.Length)`，括號裡仍會先做 `int` 乘法，溢位後才轉型就來不及了。最後整個減法算式完成後，才能依照題目保證把答案轉回 `int`。

### 正確性與複雜度

每一輪結束後，`sum` 都是已處理元素的總和，`minNum` 都是已處理元素的最小值。第一輪時兩者分別為 `nums[0]` 與 `nums[0]`；後續每輪加入當前元素並更新最小值，會持續維持這兩項性質。因此，走訪結束時兩者就是完整陣列所需的資訊，代入已推導的公式即可得到最少操作次數。

- 時間：`O(n)`，只完整走訪陣列一次。
- 額外空間：`O(1)`，只使用固定數量的變數，不修改輸入陣列。


## 解法三：自行走訪找最小值，再累加差額

對應方法：`MinMoves3(int[] nums)`。這個方法沿用解法一的差額公式，但把 `nums.Min()` 改寫成明確的 `foreach` 迴圈，方便觀察最小值如何逐步確定。它沒有使用 LINQ 的 `Min()`，仍使用內建的 `Math.Min(a, b)` 比較兩個數值；並非完全不使用內建函式。

### 設計出發點與變數

我們需要的是完整陣列的最小值，才能讓每個元素都使用相同的目標計算操作次數。因此分成兩個階段：第一階段只找最小值，第二階段才計算答案，不在最小值尚未確定時累加差額。

| 變數 | 意義與初始值 |
| --- | --- |
| `minNum` | 目前已走訪元素的最小值，初始化為 `nums[0]` |
| `x` | 當前迴圈處理的元素；兩個迴圈各自走訪完整陣列 |
| `res` | 已處理元素與最終最小值的差額總和，初始化為 `0` |

1. 題目保證陣列非空，因此用 `nums[0]` 作為最小值的起點。若以 `0` 初始化，對 `[5, 6, 1]` 就會錯誤保留不存在於陣列中的 `0`。
2. 第一次 `foreach` 逐一執行 `minNum = Math.Min(minNum, x)`，保留舊最小值與目前元素之中較小的一個。第一個元素會再比較一次，不影響結果。
3. 第一次走訪結束後，`minNum` 就是完整陣列的最小值。
4. 第二次 `foreach` 使用固定的 `minNum`，將每個 `x - minNum` 加入 `res`。
5. 回傳差額總和；過程不修改 `nums`，也不實際模擬每一步增減。

```csharp
int minNum = nums[0];
int res = 0;

foreach (int x in nums)
{
    minNum = Math.Min(minNum, x);
}

foreach (int x in nums)
{
    res += x - minNum;
}

return res;
```

### 範例演示一：`[1, 2, 3]`

初始化 `minNum = 1`、`res = 0`。第一次走訪只找最小值：

| 步驟 | 元素 `x` | 更新前 `minNum` | `Math.Min(minNum, x)`／更新後 `minNum` |
| --- | ---: | ---: | ---: |
| 1 | 1 | 1 | 1 |
| 2 | 2 | 1 | 1 |
| 3 | 3 | 1 | 1 |

第二次走訪固定使用 `minNum = 1`：

| 步驟 | 元素 `x` | 差額 `x - minNum` | 累加前 `res` | 累加後 `res` |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1 | 0 | 0 | 0 |
| 2 | 2 | 1 | 0 | 1 |
| 3 | 3 | 2 | 1 | 3 |

回傳 `3`，與前兩種解法一致。

### 範例演示二：`[5, 6, 1]`，最小值最後才出現

初始化 `minNum = 5`、`res = 0`。第一次走訪：

| 步驟 | 元素 `x` | 更新前 `minNum` | `Math.Min(minNum, x)`／更新後 `minNum` |
| --- | ---: | ---: | ---: |
| 1 | 5 | 5 | 5 |
| 2 | 6 | 5 | 5 |
| 3 | 1 | 5 | 1 |

前兩輪的最小值仍是 `5`，到第三輪才得到最終最小值 `1`。第二次走訪從頭重新讀取元素，以 `1` 為共同目標：

| 步驟 | 元素 `x` | 差額 `x - minNum` | 累加前 `res` | 累加後 `res` |
| --- | ---: | ---: | ---: | ---: |
| 1 | 5 | 4 | 0 | 4 |
| 2 | 6 | 5 | 4 | 9 |
| 3 | 1 | 0 | 9 | 9 |

回傳 `9`。若把兩個迴圈直接合併，每輪更新最小值後就累加 `x - minNum`，會得到 `0 + 1 + 0 = 1`：最後才發現的 `1` 無法自動修正前兩個元素已少算的差額。保留兩次走訪，就能確保每個差額都以最終最小值計算；若要單次走訪，可採用解法二的總和公式。

### 正確性、整數安全性與複雜度

第一次迴圈開始前，`minNum` 是第一個元素；每處理一個 `x`，`Math.Min` 都保留已讀取元素中的最小值，因此第一次走訪結束時得到全域最小值。第二次迴圈每輪將目前元素的完整差額加入 `res`，所以結束時 `res = Σ(nums[i] - minNum)`；依照前面的等價轉換與最優目標推導，這就是最少操作次數。

`int` 的安全性與解法一相同：單一差額最多為 `2_000_000_000`；每個差額皆非負，部分累加不超過題目保證可由 `int` 表示的最終答案。此保證適用於符合題目限制的輸入，並非宣稱任意整數陣列都不會溢位。

- 時間：`O(n)`，兩次完整走訪共 `O(n) + O(n)`。
- 額外空間：`O(1)`，只保留固定數量的變數，不建立新陣列。

## 三種解法比較

| 比較項目 | 解法一：`MinMoves` | 解法二：`MinMoves2` | 解法三：`MinMoves3` |
| --- | --- | --- | --- |
| 核心公式 | `Σ(nums[i] - minNum)` | `sum - n × minNum` | `Σ(nums[i] - minNum)` |
| 最小值取得方式 | LINQ `nums.Min()` | `foreach` 搭配 `if` 比較 | `foreach` 搭配 `Math.Min` |
| 走訪方式 | 先找最小值，再累加差額，共兩次 | 同時計算總和與最小值，共一次 | 先找最小值，再累加差額，共兩次 |
| 時間複雜度 | `O(n)` | `O(n)` | `O(n)` |
| 額外空間複雜度 | `O(1)` | `O(1)` | `O(1)` |
| 中間計算型別 | `int`，非負差額累加不超過最終答案 | 總和與乘積使用 `long`，最後轉回 `int` | `int`，理由與解法一相同 |
| 是否修改輸入 | 否 | 否 | 否 |
| 學習重點 | 直接實作差額公式，以 LINQ 表達最小值搜尋 | 展開公式並在一次走訪中收集資訊 | 明確展示最小值搜尋與差額累加的兩階段流程 |

三種方法在最壞情況下都必須讀取每個元素；若漏看某個元素，就可能漏掉更小的最小值或改變總和的數值，因此 `O(n)` 已達到這題的漸近最佳時間複雜度。從兩次走訪合併成一次，不會改變大 O 表示法，也不能直接推論執行時間會減半。

若著重推導直觀，可以先閱讀解法一；若想練習把公式整理成單次走訪，可以閱讀解法二；若想觀察最小值如何在迴圈中維護，可以對照解法三。解法三把最小值搜尋寫出來，有助於理解，但仍使用內建 `Math.Min`，也不代表一定比 LINQ `Min()` 快。
