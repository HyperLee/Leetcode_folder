## 題目說明

給定兩個從零開始索引的整數陣列：

| 輸入 | 意義 |
| --- | --- |
| `servers[i]` | 第 `i` 台伺服器的權重，數字越小越優先 |
| `tasks[j]` | 第 `j` 個任務需要的處理秒數，於第 `j` 秒到達 |

起初所有伺服器皆閒置。任務依到達順序排隊，每次將最前面的任務交給**權重最小的閒置伺服器**；權重相同時選**索引最小者**。全部忙碌時，任務等待到有伺服器可用。如果多台同時完成，必須讓它們全部加入候選，再依上述規則分配等待中的任務。

伺服器於時間 `t` 開始任務 `j`，便在 `t + tasks[j]` 恢復閒置；在該完成時間就能立即接下一個任務。輸出 `ans`，其中 `ans[j]` 是處理任務 `j` 的伺服器索引。

### 限制條件

依官方題目：

- `servers.length == n`、`tasks.length == m`。
- `1 <= n, m <= 200,000`。
- `1 <= servers[i], tasks[j] <= 200,000`。

本實作假設輸入符合上述限制，不另驗證空值、空陣列或非法數值。輸入陣列不會被修改。

### 官方範例

```text
範例一
servers = [3,3,2]
tasks   = [1,2,3,2,1,2]
ans     = [2,2,0,2,1,2]

範例二
servers = [5,1,4,3,2]
tasks   = [2,1,2,4,5,2,1]
ans     = [1,4,1,4,1,3,2]
```

## 解題概念與出發點

直覺作法是逐秒推進時間、檢查所有伺服器。然而當任務大量積壓，可能等待數十億秒；逐秒等待沒有產生新的分配資訊。即使跳過等待，若每個任務都線性掃描所有伺服器，也會有 `O(nm)` 的成本。

真正需要回答的只有兩個問題：

1. 現在能使用的伺服器中，誰的權重與索引最優先？
2. 如果全部忙碌，最早什麼時候有伺服器可用？

兩個問題使用不同排序，因此分別建立兩個最小優先佇列。時間只在下一個任務到達或必須等待伺服器完成時前進。

## 解題設計：雙優先佇列

專案目前只有這一種解法，公開方法為：

```csharp
public int[] AssignTasks(int[] servers, int[] tasks)
```

### 1. 分離「挑選伺服器」與「等待完成」

| 佇列 | 元素 | 優先權 | 用途 |
| --- | --- | --- | --- |
| `idle` | `(weight, idx)` | `(weight, idx)` | 取出權重最小、同權重時索引最小的閒置伺服器 |
| `busy` | `(t, idx)` | `long` 完成時間 `t` | 找出下一個完成事件，並釋放已完成者 |

C# `ValueTuple` 的預設比較依欄位順序進行，因此 `(weight, idx)` 自然符合題目規則。`busy` 的同時間元素不需要額外排序：選擇伺服器前會將所有已完成者放回 `idle`，最終由 `idle` 決定分配順序。

> [!IMPORTANT]
> 不能在全部忙碌時只取出一台最早完成的伺服器就直接分配。當多台同時完成，忙碌佇列取出的第一台未必擁有最小權重或最小索引。

#### 補充：預設比較器與自訂比較器有什麼差異？

以下兩種宣告都是 C#，在本題中會得到相同的出隊順序：**先選權重小的伺服器，權重相同時再選索引小的伺服器**。

第一種使用預設比較器：

```csharp
var idle = new PriorityQueue<(int weight, int idx), (int weight, int idx)>();
```

`PriorityQueue<TElement, TPriority>` 的第一個型別是存放的資料，第二個型別是決定出隊順序的優先權。沒有傳入比較器時，會使用 `Comparer<TPriority>.Default`；對這裡的 `(int, int)` 元組，預設採用字典序比較：先比較第一個欄位 `weight`，只有相同時才比較第二個欄位 `idx`，兩者都是較小者優先。

例如，依序加入下列資料：

```csharp
idle.Enqueue((3, 2), (3, 2));
idle.Enqueue((1, 5), (1, 5));
idle.Enqueue((3, 0), (3, 0));
```

連續呼叫三次 `Dequeue()`，取出的元素依序為：

```text
(1, 5)  // 權重最小
(3, 0)  // 權重相同時，索引較小
(3, 2)
```

注意，`Enqueue(element, priority)` **比較的是第二個參數 `priority`**。本題刻意讓元素與優先權都使用 `(weight, idx)`，才會看起來像是在直接比較元素。

第二種則自行指定比較器，明確寫出相同的比較規則：

```csharp
var idle = new PriorityQueue<(int w, int idx), (int, int)>(
    Comparer<(int, int)>.Create((a, b) =>
    {
        if (a.Item1 != b.Item1)
        {
            return a.Item1 - b.Item1;
        }

        return a.Item2 - b.Item2;
    }));
```

比較器回傳負數表示 `a` 優先於 `b`，正數表示 `b` 優先，零表示兩者優先權相同。這段程式先比較權重，再比較索引，因此在本題限制下與第一種等效。元組欄位名稱是 `weight`、`w` 或使用 `Item1` 存取，都不會改變比較規則。

一般用途的自訂比較器建議使用 `CompareTo`，避免兩個整數相減可能溢位：

```csharp
var idle = new PriorityQueue<(int weight, int idx), (int weight, int idx)>(
    Comparer<(int weight, int idx)>.Create((a, b) =>
    {
        int result = a.weight.CompareTo(b.weight);
        return result != 0 ? result : a.idx.CompareTo(b.idx);
    }));
```

本題使用預設比較器即可；需要權重由大到小、不同的欄位優先順序等規則時，再自訂比較器。

> [!NOTE]
> `PriorityQueue` 保證每次 `Peek()` 或 `Dequeue()` 取得優先權最小的元素，內部並非完整排序的陣列。透過 `UnorderedItems` 列舉內容時，不保證依優先權排列；若兩個元素的完整優先權相同，也不保證依加入順序取出。

### 2. 初始化

將全部 `n` 台伺服器加入 `idle`，`busy` 為空。目前時間 `ts = 0`，答案陣列長度為 `m`。

任意時刻，每台伺服器都恰好存在於一個佇列中。分配時從 `idle` 移入 `busy`；完成時反向移回，不複製伺服器狀態。

### 3. 依任務索引進行模擬

對任務 `i` 執行：

1. `ts = Math.Max(ts, i)`：任務不能在到達前開始，時間也不能因為積壓而倒退。
2. 呼叫 `Release`，將所有 `完成時間 <= ts` 的伺服器移回 `idle`。
3. 若 `idle` 仍為空，令 `ts = busy.Peek().t`，直接跳到最早完成時間，再次呼叫 `Release`。
4. 從 `idle` 取出最優先的伺服器，記錄到 `ans[i]`。
5. 計算 `finishTime = ts + tasks[i]`，將該伺服器加入 `busy`。

`Release` 必須使用 `while` 與 `<=`：前者一次處理所有完成者，後者包含恰好在目前時間完成的伺服器。合法輸入至少有一台伺服器，因此 `idle` 為空時，`busy` 必有元素。

### 4. 為什麼不需要額外任務佇列？

迴圈永遠先處理任務 `i`，再處理 `i+1`，這本身就維持 FIFO。當 `ts > i`，表示任務已經在等待；此時保持 `ts`，便能繼續分配積壓任務。多個任務可在相同時間開始，只要有足夠閒置伺服器，不需要強制每次分配都把時間增加一秒。

### 5. 為什麼時間必須使用 long？

單台伺服器連續處理最多 200,000 個任務，每個最多 200,000 秒，總處理時間可達：

```text
200,000 × 200,000 = 40,000,000,000
Int32.MaxValue   =  2,147,483,647
```

因此 `ts`、完成時間、忙碌佇列元素的時間欄位、忙碌優先權與 `Release` 的時間參數全部使用 `long`。只把最後的加法結果轉型，無法修復已在 `int` 加法中發生的溢位。權重、任務耗時、伺服器索引與回傳陣列仍使用 `int`。

### ASCII 整體流程

```text
[全部伺服器 -> idle；busy 空；ts = 0]
                    |
                    v
          [取下一個任務 i]
                    |
                    v
           [ts = max(ts, i)]
                    |
                    v
 [busy 中所有 t <= ts 的伺服器 -> idle]
                    |
                    v
             <idle 是否為空?>
               /          \
             是            否
              |             |
 [ts = busy 最早完成時間]    |
              |             |
 [全部 t <= ts 者 -> idle]   |
               \           /
                v         v
       [idle 取最小 (weight, idx)]
                    |
                    v
           [ans[i] = idx]
                    |
                    v
 [以 ts + tasks[i] 為完成時間加入 busy]
                    |
                    v
          <還有任務?> -- 是 --> [下一輪]
                    |
                   否
                    v
               [回傳 ans]
```

### 正確性說明

每次分配前，先將時間推進至不早於任務到達的時刻，再完整釋放所有已完成者，因而 `idle` 包含此刻全部可用的伺服器。如果它為空，在最早完成時間之前不可能開始任務，跳到該時間並完整釋放不會漏掉任何可行分配。

接著，`idle` 的排序保證選到題目要求的權重與索引；迴圈的索引順序保證先到先處理。分配後正確記錄完成時間，兩個佇列重新維持上述狀態。因此由第一個任務開始歸納，每次分配都符合規則。

### 複雜度

- 初始化逐一加入 `n` 台伺服器，耗時 `O(n log(n+1))`。
- 每個任務分配一次；每次忙碌紀錄最多釋放一次。所有任務的佇列操作合計 `O(m log(n+1))`，即使 `Release` 使用 `while`，也不會每輪掃描全部伺服器。
- 總時間為 **`O((n+m) log(n+1))`**；寫成 `log(n+1)` 可涵蓋單台伺服器。
- 兩個佇列合計保存 `n` 台伺服器，輔助空間為 **`O(n)`**；輸出陣列另占 **`O(m)`**，合計 `O(n+m)`。此分析不含主程式的測試資料與輸入備份。

## 逐步演示

以下 `S0` 表示索引 0 的伺服器；候選以 `(權重, 索引)` 排序。表格的「釋放者」是該輪從 `busy` 移回 `idle` 的伺服器。

### 範例一：相同完成時間下重新比較權重

`servers = [3,3,2]`，`tasks = [1,2,3,2,1,2]`。

| 任務 i | 到達時間 | 開始時間 ts | 釋放者 | 分配前閒置候選（優先順序） | 選中索引 | 完成時間 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 無 | S2、S0、S1 | 2 | 1 |
| 1 | 1 | 1 | S2 | S2、S0、S1 | 2 | 3 |
| 2 | 2 | 2 | 無 | S0、S1 | 0 | 5 |
| 3 | 3 | 3 | S2 | S2、S1 | 2 | 5 |
| 4 | 4 | 4 | 無 | S1 | 1 | 5 |
| 5 | 5 | 5 | S0、S1、S2 | S2、S0、S1 | 2 | 7 |

```text
t = 5：三台同時完成
busy: (5,S0), (5,S1), (5,S2)
                  |
          Release 全部移回
                  v
idle: (2,S2), (3,S0), (3,S1)
                  |
                  v
任務 5 -> S2；完成於 5 + 2 = 7
ans = [2,2,0,2,1,2]
```

### 範例二：多台閒置時仍比較權重

`servers = [5,1,4,3,2]`，`tasks = [2,1,2,4,5,2,1]`。

| 任務 i | 到達時間 | 開始時間 ts | 釋放者 | 分配前閒置候選（優先順序） | 選中索引 | 完成時間 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 無 | S1、S4、S3、S2、S0 | 1 | 2 |
| 1 | 1 | 1 | 無 | S4、S3、S2、S0 | 4 | 2 |
| 2 | 2 | 2 | S1、S4 | S1、S4、S3、S2、S0 | 1 | 4 |
| 3 | 3 | 3 | 無 | S4、S3、S2、S0 | 4 | 7 |
| 4 | 4 | 4 | S1 | S1、S3、S2、S0 | 1 | 9 |
| 5 | 5 | 5 | 無 | S3、S2、S0 | 3 | 7 |
| 6 | 6 | 6 | 無 | S2、S0 | 2 | 7 |

```text
t=0   t=1   t=2   t=3   t=4   t=5   t=6
 |     |     |     |     |     |     |
 J0    J1    J2    J3    J4    J5    J6
 |     |     |     |     |     |     v
 S1    S4    S1    S4    S1    S3    S2

ans = [1,4,1,4,1,3,2]
```

回傳答案只需要確定每個任務分配給誰，不必模擬到所有任務完成。

### 積壓與時間跳躍

`servers = [2,1]`，`tasks = [5,5,1,1,1]`。

| 任務 i | 到達時間 | 開始時間 ts | 釋放者 | 選中索引 | 完成時間 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 無 | 1 | 5 |
| 1 | 1 | 1 | 無 | 0 | 6 |
| 2 | 2 | 5（等待） | S1 | 1 | 6 |
| 3 | 3 | 6（等待） | S0、S1 | 1 | 7 |
| 4 | 4 | 6 | 無，S0 已在上一輪釋放 | 0 | 7 |

```text
到達： t=0 J0   t=1 J1   t=2 J2   t=3 J3   t=4 J4
                         |         |         |
                         +---------+---------+--> 等待

分配： t=0 J0->S1
       t=1 J1->S0
       t=2 無閒置 --> 直接跳 t=5：J2->S1
       t=5 無閒置 --> 直接跳 t=6：先釋放 S0、S1
                                  |
                                  +-> J3->S1（權重 1）
                                  +-> J4->S0（權重 2）

ans = [1,0,1,1,0]
```

任務 3 與 4 都在時間 6 開始，仍依原始任務順序分配。若同時釋放者權重相同，例如 `servers = [1,1]`、`tasks = [3,2,1,1]`，兩台在時間 3 完成，先將任務 2 分配給 S0，再將任務 3 分配給 S1，答案為 `[0,1,0,1]`。
