## 題目說明

給定一個由 `n` 個節點組成的無向星型圖，節點編號為 `1` 到 `n`。星型圖只有一個中心節點，中心會透過 `n - 1` 條邊分別連接其他所有節點，而其他節點彼此不相連。

輸入為二維整數陣列 `edges`，其中 `edges[i] = [ui, vi]` 表示節點 `ui` 與 `vi` 之間存在一條無向邊。目標是回傳唯一的中心節點編號。

### 官方範例一

```text
輸入：edges = [[1,2],[2,3],[4,2]]
輸出：2
```

節點 `2` 分別與 `1`、`3`、`4` 相連，因此中心是 `2`。

### 官方範例二

```text
輸入：edges = [[1,2],[5,1],[1,3],[1,4]]
輸出：1
```

節點 `1` 出現在所有邊中，並連接其餘四個節點，因此中心是 `1`。

### 限制條件

- `3 <= n <= 10^5`
- `edges.Length == n - 1`
- `edges[i].Length == 2`
- `1 <= ui, vi <= n`
- `ui != vi`
- 題目保證 `edges` 描述的是合法星型圖。

本專案依照 LeetCode 的合法輸入契約實作，不額外處理空陣列、少於兩條邊、節點編號越界或不是星型圖的輸入。

題目連結：[1791. Find Center of Star Graph](https://leetcode.com/problems/find-center-of-star-graph/)

## 解題概念與出發點

星型圖有兩個非常重要的性質：

1. 中心節點出現在每一條邊中，因此總共出現 `n - 1` 次。
2. 任取兩條不同的邊，它們唯一的共同端點必定是中心。

從第一個性質可以直接統計所有節點的出現次數，這形成解法一。第二個性質進一步告訴我們，其實不必走訪全部資料，只比較前兩條邊就能找到中心，這形成解法二。

若希望保留「中心必須存在於每條邊」的直觀驗證過程，又不想配置字典，可以先從第一條邊取得兩個候選。只要第一個候選被任何一條邊排除，另一個候選依合法星型圖契約就必定是中心；這形成解法三。

三種方法共同遵守以下契約：

- 輸入必須是合法星型圖。
- 回傳唯一的中心節點編號。
- 只讀取 `edges`，不修改外層陣列或任何內層邊陣列。

## 解法一：字典統計法

API：`FindCenter(int[][] edges)`

### 設計步驟

1. 建立 `Dictionary<int, int>`，鍵是節點編號，值是該節點出現在邊集合中的次數。
2. 走訪每條邊的兩個端點，將對應節點的次數加一。
3. 統計完成後，尋找出現次數等於 `edges.Length` 的節點。
4. 回傳該節點；題目保證合法星型圖，所以一定存在且只有一個符合者。

### 為什麼正確

星型圖共有 `n - 1` 條邊，每條邊都由中心連向一個不同的外圍節點。因此中心恰好出現在全部 `n - 1` 條邊中，而每個外圍節點只出現一次。當某個節點的累計次數等於總邊數時，該節點必定是中心；反過來，中心也一定滿足此條件。

### 複雜度與輸入副作用

- 時間複雜度：O(n)。每條邊的兩個端點各統計一次，再掃描字典。
- 額外空間複雜度：O(n)。字典最終保存所有節點的次數。
- 輸入副作用：無，只讀取 `edges`。

### 範例演示：官方範例一

`edges = [[1,2],[2,3],[4,2]]`，總邊數為 `3`。

| 步驟 | 讀取的邊 | 更新後的出現次數 | 判斷 |
| ---: | --- | --- | --- |
| 1 | `[1,2]` | `1:1, 2:1` | 尚無節點出現 3 次 |
| 2 | `[2,3]` | `1:1, 2:2, 3:1` | 節點 2 目前出現 2 次 |
| 3 | `[4,2]` | `1:1, 2:3, 3:1, 4:1` | 節點 2 的次數等於總邊數 |

因此回傳 `2`。

## 解法二：前兩條邊判斷法

API：`FindCenter2(int[][] edges)`

### 設計步驟

1. 將前兩條邊視為 `[a,b]` 與 `[c,d]`。
2. 檢查 `a` 是否等於 `c` 或 `d`：
   - 若是，`a` 同時存在於前兩條邊，所以 `a` 是中心。
   - 若否，合法星型圖仍必須有共同端點，因此 `b` 一定是中心。
3. 直接回傳判斷結果，不需要走訪其餘邊。

### 為什麼正確

題目保證輸入是合法星型圖，而中心會存在於任意一條邊。前兩條邊唯一重複的節點就是中心。第一條邊只有 `a`、`b` 兩個可能：若 `a` 也出現在第二條邊，答案就是 `a`；否則共同端點只能是 `b`。後續邊不可能推翻這個結論。

### 複雜度與輸入副作用

- 時間複雜度：O(1)。固定讀取四個端點並進行至多兩次相等比較。
- 額外空間複雜度：O(1)。不建立與輸入規模相關的資料結構。
- 輸入副作用：無，只讀取前兩條邊。

### 範例演示：官方範例二

前兩條邊是 `[1,2]` 與 `[5,1]`，可令 `a = 1`、`b = 2`、`c = 5`、`d = 1`。

| 比較 | 結果 | 說明 |
| --- | --- | --- |
| `a == c`，即 `1 == 5` | `false` | 第一個位置不相同 |
| `a == d`，即 `1 == 1` | `true` | 節點 1 同時存在於兩條邊 |

條件成立，因此直接回傳 `a`，答案是 `1`。其餘兩條邊不需讀取。

## 解法三：首邊候選驗證法

API：`FindCenter3(int[][] edges)`

### 設計步驟

1. 第一條邊的兩個端點一定包含中心，將第一個端點保存為 `firstCandidate`，另一端點保留為備選答案。
2. 由第一條邊開始逐邊檢查 `firstCandidate` 是否為其中一個端點。
3. 若遇到任何一條邊不包含 `firstCandidate`，第一個候選不可能是中心；依合法星型圖契約，立即回傳第一條邊的另一端點。
4. 若全部邊都包含 `firstCandidate`，回傳第一個候選。

### 為什麼正確

中心必定存在於第一條邊，所以答案只能是第一條邊的兩個端點之一。若第一個候選存在於每條邊，它符合中心的定義；若它缺席於任何一條邊，它就不可能是中心。此時第一條邊剩下的另一端點是唯一仍可能的候選，而題目又保證圖合法，因此該端點必定是中心。

這個方法與字典法都使用「中心出現在每條邊」的性質，但只追蹤兩個候選，不統計所有節點；與前兩邊判斷法相比，它保留了逐邊驗證候選的過程。

### 複雜度與輸入副作用

- 時間複雜度：最壞 O(n)。第一個候選若真是中心，必須檢查全部邊；若候選提早被排除則可提前結束。
- 額外空間複雜度：O(1)。只保存一個候選節點。
- 輸入副作用：無，只讀取 `edges`。

### 範例演示：邊順序與中心位置交錯

`edges = [[6,3],[1,3],[3,5],[2,3],[3,4]]`。

第一條邊是 `[6,3]`，因此 `firstCandidate = 6`，另一個候選是 `3`。

| 步驟 | 檢查的邊 | 是否包含候選 6 | 動作 |
| ---: | --- | --- | --- |
| 1 | `[6,3]` | 是 | 繼續檢查 |
| 2 | `[1,3]` | 否 | 排除 6，回傳另一候選 3 |

因為輸入保證是合法星型圖，排除 `6` 後不必再次驗證 `3`，答案就是 `3`。

## 三種解法比較

| 項目 | 字典統計法 | 前兩條邊判斷法 | 首邊候選驗證法 |
| --- | --- | --- | --- |
| 方法 | `FindCenter` | `FindCenter2` | `FindCenter3` |
| 核心觀察 | 中心出現次數等於總邊數 | 任意兩條邊共享中心 | 第一條邊包含全部可能候選 |
| 讀取範圍 | 全部邊與全部節點 | 只讀前兩條邊 | 最壞讀取全部邊，可提前結束 |
| 時間複雜度 | O(n) | O(1) | O(n) |
| 額外空間 | O(n) | O(1) | O(1) |
| 是否修改輸入 | 否 | 否 | 否 |
| 教學價值 | 直接呈現節點度數／出現次數 | 展示如何利用題目保證消除遍歷 | 展示候選排除與迴圈不變量 |

實務上，若完全信任題目提供合法星型圖，`FindCenter2` 最精簡且效率最佳；字典法較接近一般圖論中的度數統計；候選驗證法則介於兩者之間，保有直觀驗證流程且不需要額外集合。

## 可執行測試資料

`Main` 固定執行五組合法星型圖：兩個官方範例、中心分別位於第一欄與第二欄的最小三節點圖，以及中心位置與邊順序交錯的較大案例。

每組案例對三種解法各執行兩項檢查：

1. 實際回傳值等於手動指定的 `Expected`。
2. 執行後的二維 `edges` 仍與執行前完全相同。

因此共有 `5 組案例 × 3 種解法 × 2 項檢查 = 30` 項檢查。每種解法都取得獨立的深層副本，避免未來某個實作改為會修改輸入時污染其他解法的案例。任一檢查失敗時，主控台會顯示 `FAIL`，程序結束碼也會設為 `1`。
